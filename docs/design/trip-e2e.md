# 席を持つメンバーにだけ読める旅程 — 旅行の鍵の作り方・配り方（Spike #520）

親 PBI: #520。元要望: #519（運用者が 1 人であることを理由にしない。オーナーでない人が読めるのは許さない）。前例: `docs/design/private-entries-e2e.md`（#343 の席ごとのメモの鍵。パスキーの PRF で包む）。

この文書は方式を決める Spike の成果物で、実装はしていない。試したコードはコミットせず、§2.6 に載せた。行番号・一次資料は 2026-10-06 の main（`cabe854`）で確かめた。**実機のスマホでは試していない**。§0〜§2 と §7 の枠は #525 が 2026-10-06 の main（`cabe854`）で、§3〜§6 は #526 が 2026-10-07 の main（`0d154f0`）で書き、§7 の決定と §3.1・§5・§6 の文言の直しは #527 が同じ日に足した。§1・§2 の行番号は `cabe854`、§3〜§6 は `0d154f0` のもの。

## 0. 結論

2026-10-07 に利用者が案 A（確認コード）に決めた（§7）。

**推薦: 案 A（新メンバーのブラウザが鍵の組を作り、鍵を持つメンバーのブラウザが Host を中継して旅行の鍵を包む。包む前に、両方の画面に出る 6 桁の確認コードを別の経路（チャット・口頭）で伝え合い、互いに相手のコードを入力する）。**

旅行ごとにランダムな「旅行の鍵」（AES-GCM 256）を 1 本作り、旅程をそれで暗号化して置く。席ごとに「席の鍵の組」（X25519）を持ち、旅行の鍵は席の公開鍵へ包んで席に置く。席の秘密鍵は、席のパスキーの PRF で包んで席に置き（#343 と同じ置き方）、開いた端末では取り出せない `CryptoKey` として IndexedDB に持つ。確かめ合った 2 つの席は互いの公開鍵に署名（Ed25519）し、鍵を替えるとき owner のブラウザは、手元の自分の署名の鍵から失効していない席どうしの署名をたどれる公開鍵だけへ包み直す。3 案の違いは「新メンバーの公開鍵が本当にその人のものか（と、届いた旅行の鍵が本物か）」を何で確かめるかだけ（§2.1）。

理由:

1. `crypto.subtle` の X25519・Ed25519・HKDF・AES-GCM だけで作れる（X25519 は Chrome / Edge 133、Firefox 130、Safari 17 以降。Ed25519 は Chrome / Edge 137、Firefox 129、Safari 17 以降。手元の Chrome で鍵の組から旅行の鍵を包んで開けた。§2.5、§2.6）。案 C の PAKE は WebCrypto に無く、楕円曲線への写像を自前で書くか依存を足すことになる。案 B は QR を描く部品が要る
2. 対面でも離れていても使える。確認コードは秘密ではなく、旅行の連絡に使っているチャットに貼ってよい（運用者は Host を握るが、そのチャットは握らない）。案 B は同じ場所にいるときしか使えず、案 C のコードは使うまで秘密にしておく必要がある
3. 運用者が Host で公開鍵をすり替えても、偽の旅行の鍵を渡そうとしても、確認コードが合わず包まない・受け取らない。新メンバーが先に公開鍵のハッシュだけを預けるので（§2.1 の手順 1）、運用者が一致するコードを探して鍵を作り直すことはできず、すり替えが通るのは 1 回の試みにつき 100 万分の 1。失敗は画面に出る

暗号化するのは中身（題・本文・場所・名前・金額・居場所・写真）で、日付・時刻・件数・役割・だれの記録かは平文に残す（§3）。Host は予定の時刻の決定と役割の検査を続け、書き出し・改訂・中身の検査はブラウザに移る（§4）。平文で置かれている旅行は、owner が新しい画面で開いたときに移す（§5）。実装は 8 PBI・38 ポイントの目安（§6）。鍵を替える扱い（§2.1 の「実装の PBI で決めること」）は §8 で決めた。

退けた 3 案（§2.4）は比較の候補に入れていない。どの案も、鍵の預かり・運用者による回復は持たない（運用者が復号できるなら「読めない」ではない）。

## 1. 今だれが旅程を読めるか

共有の旅程（`spec` と `document`。予定・準備リスト・メモ・予算・提案・コメント・思い出）と足あとは、カプセルの payload に平文の JSON で入る。読めるのは次の経路。

| 経路 | だれが | 何が読めるか | コードの場所 |
|---|---|---|---|
| DynamoDB を読む | 運用者（AWS アカウントの IAM で DynamoDB を読める人） | payload の全部。旅程・足あと（`Capsule.footprints`）・メンバーの名前。自分だけの予定・日記の題・本文・場所だけは暗号文（#343） | テーブル `aws/template.yaml:33`、保存時の暗号化は AWS の鍵（`aws/template.yaml:54`）で、IAM で読めれば平文で返る。payload は 128 KiB ごとに分けるだけ（`src/aws-store.ts:7-12`）で、`get` が連結して文字列に戻す（`src/aws-store.ts:16-22`）。足あとは暗号化しないと型に書いてある（`src/cloud-host.ts:24-27`） |
| `aws/recover.ts` → `route` の `recover` | IAM の発行者（運用者と同じ人のことが多い） | 新しい owner の招待リンク。開けば owner の席になり、`GET` で旅程を全部読める（`src/cloud-host.ts:609`）。旅程を読む権限は席に付くので、席を出し直せる人は読める | `aws/recover.ts:6`、`src/cloud-host.ts:567-573`（owner の招待をすべて失効し、新しい招待を出す） |
| 作成者が作る | 作成者（パスキーでサインインした人。`docs/ephemeral-trip-capsule.md` §2.6） | 自分が書いた旅程そのもの（書いた本人なので避けられない）。保存の後は読めない（`docs/ephemeral-trip-capsule.md:370`「作れるが読めない」）。ただし、オーナーを決めていない旅行の一覧に題名・日程・削除予定が出る（`src/cloud-host.ts:260`） | 画面が平文の `spec` / `document` を送り（`src/client.ts:878`）、Host が検査して平文で置く（`src/cloud-host.ts:466-491`）。**暗号化するなら、だれが初めに暗号化するか**が問題になる（§2.2） |
| CLI で発行する | IAM の発行者 | 手元の入力ファイル（平文）。送るのも平文の `spec` / `document` | `aws/publish.ts:9-10`（読んで検査）、`aws/publish.ts:39`（送る） |
| 文書の前提 | — | 「データストアを読める IAM の権限があれば、旅程も読める（アプリ層では暗号化していない）」「運用者は**信頼境界の内側**」 | `docs/ephemeral-trip-capsule.md:345`（運用者の回復権限の行）。#520 の起票時に `:329` と書いた行と同じ行（その後の追記で行番号が動いた） |

一方で、文書は「Publisher は旅程のセッションを得ない」（`docs/ephemeral-trip-capsule.md:303`）、作成者は「作れるが読めない」（同 `:370`）と書く。#519 の「今の権限分けと整合しない」は、この 2 行と上の表の 1・2 行目が食い違っていること。

**この Spike が閉じる経路**: 1 行目（保存されたデータを後から読む）と 2 行目（席を出し直して読む）。2 行目は、席を出せても旅行の鍵を渡すのはメンバーなので、メンバーが確かめずに鍵を渡さない限り読めない（§2.3 の表 1）。

**閉じない経路**: 画面の JavaScript は運用者が配る（S3 の `dist/public/`）。復号した旅程を送り返すコードを配れば読める（PBI のスコープ外。`docs/design/private-entries-e2e.md` §1 と同じ）。メンバーが旅程を書き出して渡す・画面を撮って渡すことも防がない。

## 2. 旅行の鍵の作り方・配り方

### 2.1 3 案に共通する形と、違うところ

**鍵の形（3 案とも同じ）**:

- **旅行の鍵**: AES-GCM 256 を 1 本。世代の番号を付ける（替えたら 1 つ増やす。§2.3 の表 3）。旅程の暗号文の形は #526（§3）で決める
- **席の鍵の組**: 席ごとに X25519（包むため）と Ed25519（署名のため）の鍵の組を持つ。公開鍵は、初めて旅行の鍵を受け取るとき（案 A の手順 3 など。旅行の鍵を作った owner は作ったとき。§2.2）に席（`Session`）に置き、それより前には Host に出さない。秘密鍵は、#343 のメモの鍵と同じく、席のパスキーの PRF から導いた鍵で包んで席に置き、開いた端末では取り出せない `CryptoKey` として IndexedDB に置く（`src/private-entries.ts:26-33`）。パスキーの無い席は IndexedDB にだけ置く
- **席に置く旅行の鍵**: 鍵を持つメンバーのブラウザが、使い捨ての X25519 の鍵の組を作り、それと席の公開鍵との ECDH → HKDF-SHA-256 → AES-GCM で旅行の鍵を包む（HPKE の Base モードと同じ形）。包んだものと使い捨ての公開鍵を席に置く。旅行の鍵を替えるとき、相手がその場にいなくても、席の公開鍵さえあれば包み直せる
- **確かめた公開鍵の名簿**: 包む先の公開鍵を確かめたら（下の 3 案のどれか。両方の席の公開鍵を確かめる）、両方のブラウザが相手の席の公開鍵に Ed25519 で署名して席に置く（2 つの席を結ぶ**辺**）。旅行の鍵を替えるとき（§2.3 の表 3）、owner のブラウザは、手元に持つ自分の鍵から失効していない席どうしの辺をたどれる席にだけ包み直し、たどれない席は確認コードからやり直す。Host が配る公開鍵をそのまま信じないため
- **3 案に共通の限界**: 抜けた人と運用者が組めば、鍵を替えても以後の変更を読まれうる（運用者が抜けた人の席を Host に残す、抜けた人が新しい世代の鍵を置く、など。メンバーのブラウザはだれが抜けたかを Host からしか知れない）
- **実装の PBI で決めること**: 新しい世代の鍵の出どころの確かめ方、抜けた席の記録の持ち方、後からパスキーを登録した席の鍵の組の扱いは 3 案に共通で、案の選び方に関わらないので、実装の PBI（#526 の §6）で決める。そのうち後からパスキーを登録した席は #689 で決めた: 辺の署名が無い間は、席の鍵の組を作り直して旅行の鍵を新しい公開鍵へ包み直し、PRF で包んだ秘密鍵と一緒に置く（IndexedDB の秘密鍵は取り出せず、包み直せないため）。辺ができた後の扱いは §6 の 7 で決め直す。確認コードの受け渡し（#690）が決めたこと: 辺は `Session.seatKey.edges` に置く。席の鍵の組を作り直すと（後からパスキーを登録したとき）、その席の辺は消え、相手の辺はたどれなくなる（§6 の 7 で確認コードからやり直す）
- **だれが包めるか**: 旅行の鍵を持つメンバーならだれでも（役割を問わない）。席はもう owner の招待で決まっているので、鍵を渡しても席は増えない。owner しか渡せないと、owner が来ない間はだれも読めない

**3 案の違い**: 席の公開鍵は Host を通って届く。運用者は Host を握っているので、その公開鍵を自分のものにすり替えられる（退けた「Host が配る公開鍵をそのまま信じる」）。3 案は、**鍵を持つメンバーが、包む先の公開鍵を何で確かめるか**が違う。

- **案 A: 確認コード**（Host が中継。対面でも離れていても）
  1. 新メンバーのブラウザは、試みるたびに 16 バイトの乱数を作り、席の公開鍵（X25519・Ed25519）と乱数をつないだものの SHA-256（コミットメント）だけを Host に預ける（試みるたびに中身が変わるので、1 度失敗した後も、運用者は前の試みで見た値から一致するコードを探せない）
  2. 鍵を持つメンバーの画面に「メンバー3 が鍵を待っています」が出る。「渡す」を押すと、そのブラウザが使い捨ての鍵の組を作り、その公開鍵と自分の席の公開鍵（X25519・Ed25519）を一緒に Host に置く。渡す側のブラウザは、手順 1 のハッシュを、自分の値を Host に置く前に読んで手元に控え、手順 3 ではその控えと照らす（後で Host から読み直さない）。新メンバーのブラウザは、この 3 つを受け取って手元に控えてから手順 3 に進み、確認コードにはこの控えを使う（`Session` から後で読み直さない。運用者が新メンバーの公開鍵を見てから渡す側の鍵を作り替えて、コードを合わせることができないように）
  3. 新メンバーのブラウザは、それを見てから、席の公開鍵と乱数を Host に置く（手順 1 のハッシュと合うかを、渡す側のブラウザが確かめる）
  4. 両方のブラウザが、公開鍵の全部（手順 2 の渡す側の使い捨ての鍵と、渡す側の席の X25519・Ed25519 公開鍵、手順 3 の新メンバーの席の X25519・Ed25519 公開鍵と乱数）の SHA-256 から 6 桁の確認コードを 2 つ出す（ハッシュの別の部分から、新メンバーの側のコードと渡す側のコード）。互いに自分の画面のコードをチャットか口頭で伝え、相手のコードを入力する。渡す側のブラウザは、入力が合えば旅行の鍵を包んで置く。両方のブラウザは、入力が合ったら相手の席の公開鍵に署名して辺を作る（§2.1 の名簿）。包むのは手順 2 の使い捨ての鍵（§2.1 の形の使い捨ての鍵の代わり）で、新メンバーのブラウザは、入力が合ったときだけ、確かめたその公開鍵で包みを開いて旅行の鍵を受け取る。どちらかが合わなければ何も置かず・受け取らず、「確認コードが違います。もう一度やり直してください」と出す
  - 手順 1 があるので、運用者は両方の公開鍵を見てから一致するコードを探すことができない（ZRTP のハッシュコミットメントと同じ理屈。§2.5）。すり替えが通るのは 1 回につき 100 万分の 1
  - 「一致」ボタンではなく入力にするのは、見比べずに押すことを避けるため。両方が入力するのは、守るものが両側にあるため: 渡す側は旅行の鍵を運用者に渡さないこと、新メンバーは運用者が作った偽の旅行の鍵を受け取らないこと（受け取ると、その人が書いたものを運用者が読める）。運用者は本物のメンバーのチャットにいないので、偽の渡す側を演じても、新メンバーに正しいコードを伝えられない
- **案 B: 対面の QR**（Host は使い捨ての合図を見ない）
  1. 鍵を持つメンバーの画面が、使い捨ての 16 バイトの合図 `t`（5 分で失効）を入れた URL を QR で出す（`/c/<id>#pair=<t>`。`#` の後は Host に送られない）
  2. 新メンバーが、席を持つ端末の OS のカメラでその QR を読む。開いたページで、ブラウザが自分の席の公開鍵（X25519・Ed25519）と、`t` を鍵にしたその HMAC を Host に置く。OS のカメラが開くのは既定のブラウザなので、席もそこにある前提（招待リンクは `openExternalBrowser=1` で LINE のアプリ内ブラウザから既定のブラウザへ渡す。`src/cloud-host.ts:159-160`）。アプリ内ブラウザに席がある人は、席のあるブラウザでその URL を開き直す
  3. 渡す側のブラウザが HMAC を確かめ、合えば旅行の鍵を包んで、包んだものと自分の席の公開鍵（X25519・Ed25519）に `t` の HMAC を付けて置く（新メンバーのブラウザは、偽の旅行の鍵・偽の渡す側でないことをこれで確かめる）。両方のブラウザは、`t` で確かめた相手の席の公開鍵に署名して辺を作る
  - `t` は 1 回使えば、漏れても何も得られない（旅行の鍵は `t` から導けない）。この点が、退けた「旅行の鍵をリンクに載せる」と違う。ページの中でカメラを使わない（`Permissions-Policy` の `camera=()` はそのまま。`src/cloud-host.ts:827`）
  - 新メンバーが PC で、カメラで読めないときは向きを逆にする（新メンバーの PC が QR を出し、渡す側のスマホで読む。開くのは渡す側のスマホの既定のブラウザで、そこに渡す側の席が要る）
- **案 C: 1 回限りの受け渡しコード（PAKE）**（Host が中継）
  1. 鍵を持つメンバーの画面が 1 回限りの 8 桁のコード（10 分で失効）を出す。チャットか口頭で新メンバーに伝える
  2. 両方のブラウザが、そのコードを合言葉にして CPace（平衡型 PAKE）を Host 経由で 1 往復し、できた鍵が同じかを確かめ合う（鍵の確認）。合えば両方に同じ強い鍵ができ、両方のブラウザはその鍵による HMAC を付けて自分の席の公開鍵（X25519・Ed25519）を置く。渡す側は新メンバーの HMAC を確かめてから、§2.1 の形で席の公開鍵へ旅行の鍵を包み、包んだものにもその鍵の HMAC を付ける。新メンバーは、その HMAC で偽の旅行の鍵・偽の渡す側でないと確かめる。両方のブラウザは、確かめた相手の席の公開鍵に署名して辺を作る
  3. 1 つのコードで試せるのは 1 回だけ。数えるのは Host ではなく渡す側のブラウザで、鍵の確認が 1 回失敗したらコードを捨て、新しいコードを出し直す（Host は運用者が握るので、Host の回数制限には頼らない）
  - **退けた「合言葉」との違い**: 合言葉の案は、利用者が覚える長く使う言葉から PBKDF2 で鍵を導き、salt と暗号文を Host に置く。運用者は手元で総当たりできる（`docs/design/private-entries-e2e.md` §0 の理由 2）。案 C のコードは画面が作る使い捨ての値で、旅行の鍵は導かない。PAKE は中継する者にも手元での総当たりを許さず、1 回のやり取りで 1 つしか試せない（§2.5）。使った後のコードは、漏れても何も得られない
  - コードは使うまで秘密。チャットが漏れれば、先にそのコードを使った者が鍵を得る（席を持つ人に限る）

### 2.2 初めに暗号化するのはだれか

作成者のブラウザと CLI は平文の旅程を Host に送り、Host が検査して置く（§1 の 3・4 行目）。3 案とも、**初めの暗号化は owner の席を初めて取ったブラウザがする**ことを推薦する: owner のブラウザが旅行の鍵を作り、`spec` / `document` を暗号化して置き直し、平文を消す。そのブラウザが最初の「鍵を持つメンバー」になる。

- 作成者・CLI の流れと、Host の検査（`/v1/check`、`/v1/publish`）は変えない。平文の旅行を移す流れ（#526 の §5）と同じ道になる
- 平文で置かれるのは、発行から owner が席を取るまで（受付は 3 日。`src/device.ts:8` の `CLAIM_WINDOW`、`src/cloud-host.ts:152` で使う。owner が席を取らなければ、削除期限か、`/recover` で出し直した招待が引き換えられるまで。§5）。その間、運用者は DynamoDB で読める。作成者と CLI の発行者は書いた本人なので、新しく読まれる人はいない
- 作成者のブラウザで暗号化する形（作成者が鍵を作り、owner に渡したら捨てる）は、「オーナーリンクを受け取る」で別の端末・別の人に渡すとき、作成者が鍵を渡すために残ることになり、「作れるが読めない」と合わない。CLI では発行者の手元に鍵が残る

### 2.3 比べる

| 場面 | 替えるか | 理由 |
|---|---|---|
| まだだれも引き換えていない招待の失効（`revoke` の `id`、`src/cloud-host.ts:633-636`） | 替えない | 鍵を得た人がいない |
| owner 以外の招待の交換（`grants` の `rotate`。その招待の席も消える、`src/cloud-host.ts:622`） | 消えた席が鍵を持っていたら替える | 抜けた人の端末の古い鍵で、運用者と組めば以後の変更も読めてしまう |
| メンバーの失効（`revoke` の `member`、`src/cloud-host.ts:627-632`） | 替える | 同上。失効は owner がパスキーで確かめてする操作（`this.verified`）で、owner のブラウザはその場にいる（鍵をまだ持たない owner なら、鍵を得たときに替える） |
| owner の招待の交換（owner が別の端末・別の人に渡す。`rotate` で古い owner の席も消える、`src/cloud-host.ts:622`、画面は `src/client.ts:755`） | その場では替えられない。新しい owner が鍵を得た後、別の人に渡したのなら替える | 古い owner の席は同じ操作で消えるので、そのブラウザは鍵を替えも渡しもできない。新しい owner は、鍵を持つ他のメンバーと確認コードを合わせて鍵を得て、`/recover` と同じく画面が「前のオーナーの端末で読める鍵のままです。鍵を替えますか」と聞く（同じ人が端末を替えただけなら替えなくてよい。古い端末を手放すなら替える）。**他に鍵を持つメンバーがいなければ、旅程はだれにも読めなくなる**。どう防ぐかは実装で決める（§6 の 7） |
| `/recover`（古い owner の招待と席が消える） | 替えない（替えられない） | 替えるのは鍵を持つ人だけで、発行者は持たない。新しい owner が鍵を持つメンバーと確認コードを合わせて鍵を得た後、画面が「前のオーナーの端末で読める鍵のままです。鍵を替えますか」と聞く |
| 共有の終了（`freeze`。owner 以外の席が消える、`src/cloud-host.ts:729`） | 替えない | 終了の後は旅程が変わらない。抜けた人は終了までの旅程を全部見ている |
| 期限による席の失効（招待の期限切れ） | 旅行の削除期限まで続く招待なら替えない。それより短い招待の席が消えたら、次に owner が開いたときに替える | 削除期限まで続く招待は削除期限に揃う（`src/cloud-host.ts:383`）ので、旅行ごと消える。短い招待（owner が `expiresAt` を決めた、`src/cloud-host.ts:620`）の期限にはだれのブラウザもその場にいないので、owner の画面が後で替える |

替えた後の古い世代の鍵は捨てる（旅程は新しい鍵で全部暗号化し直す）。替える前に置いた画像などの大きなもの（#437）を暗号化し直すかは #526（§3、§6）で決める。

### 2.5 一次資料（確認日 2026-10-06）

- MDN の互換性データ（`@mdn/browser-compat-data` 8.1.4、2026-10-01 生成）: `SubtleCrypto` の `generateKey` / `deriveBits` / `deriveKey` の X25519 は Chrome 133 / Chrome Android 133 / Edge 133 / Firefox 130 / Firefox Android 130 / Safari 17 / Safari iOS 17。Ed25519 の `generateKey` は Chrome 137 / Chrome Android 137 / Edge 137 / Firefox 129 / Firefox Android 129 / Safari 17 / Safari iOS 17（名簿の辺。§2.1）。<https://unpkg.com/@mdn/browser-compat-data/data.json>。MDN「SubtleCrypto: deriveKey()」の X25519 の節 <https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/deriveKey>
- 同じ互換性データの `BarcodeDetector`（ページの中で QR を読む API）: Chrome は ChromeOS と macOS だけ、Chrome Android 83、Safari / Safari iOS 17 は設定のフラグ（「Shape Detection API」）を入れたときだけ、Firefox は未対応。案 B がページの中でカメラを使わず OS のカメラに任せるのはこのため。<https://wicg.github.io/shape-detection-api/#barcode-detection-api>
- RFC 6189（ZRTP）4.4.1.1:「The hash commitment precludes this attack by forcing the MiTM to choose his own two DH public values before learning the public values of either of the two parties.」「A 16-bit SAS, for example, provides the attacker only one chance out of 65536 of not being detected.」案 A の手順 1 はこれと同じ。<https://www.rfc-editor.org/rfc/rfc6189.html>
- draft-irtf-cfrg-cpace（版 21、2026-04-23）: CPace は低エントロピーの合言葉から「derive a strong shared key without disclosing the secret to offline dictionary attacks」、攻撃者には「at most one single password guess per active interaction」。X25519 で使うには RFC 9380 の Elligator2 の写像（`map_to_curve_elligator2`）、ristretto255 なら群の要素の導出が要る。<https://datatracker.ietf.org/doc/draft-irtf-cfrg-cpace/>。WebCrypto にはどちらも無い（§2.6 の 4）ので、案 C は写像を自前で書くか、楕円曲線のライブラリを依存に足す（足すなら `bun pm licenses` で確かめる。CLAUDE.md）
- パスキーの PRF のブラウザ対応と、Safari の 7 日の削除は `docs/design/private-entries-e2e.md` §2.2（2026-09-29 確認）をそのまま使う。#343 は席の秘密鍵の包み方にも使える

const a = await s.generateKey({ name: "X25519" }, false, ["deriveBits"]), b = await s.generateKey({ name: "X25519" }, false, ["deriveBits"]);

// a の秘密鍵と b の公開鍵で包み、b の秘密鍵と a の公開鍵で開いて、旅行の鍵で暗号化した "目印 trip" を復号する
// 2. P-256 の ECDH（古いブラウザ向けの代わり）で両側の値が同じか
// 3. 2 つの公開鍵の SHA-256 から 6 桁の確認コード
// 4. generateKey({ name: "CPace" | "SPAKE2" | "OPAQUE" | "hash-to-curve" })
// 5. typeof BarcodeDetector
// 6. 取り出せない（extractable: false）Ed25519 の鍵の組で "1/seat/pub" に署名し、そのままと 1 文字変えたもので検証する
```

出力:

```

p256:    {"sameSecret":true,"publicKeyBytes":65}
sas:     "6 digits"

読み取れること:

1. X25519 の鍵の組は取り出せない秘密鍵のまま ECDH に使え、HKDF から導いた鍵で旅行の鍵（32 バイト → 包んで 48 バイト）を包んで開けた。案 A・B・C の共通の形（§2.1）と案 A の確認コードは `crypto.subtle` だけで足りる。新しい依存は要らない
2. P-256 の ECDH も動く（公開鍵 65 バイト）。X25519 の無い古いブラウザ（Chrome 132 以前、Safari 16 以前）でも同じ形にできる。Ed25519 は Chrome 137 からなので、Chrome 133〜136 では署名に ECDSA（P-256）の代わりも要る。2 つの曲線を持つと画面の説明と試験が 2 通りになる。どちらにするかは #526（§6）で決める
3. WebCrypto に PAKE も hash-to-curve も無い。案 C は依存か自前の実装が要る
4. Linux の Chrome には `BarcodeDetector` が無い（MDN のとおり）。案 B はページの中で QR を読めない端末を前提にし、OS のカメラに任せる。QR を**描く**部品も WebCrypto には無く、自前で書くか依存を足す
5. Ed25519 の署名（名簿の辺）も取り出せない秘密鍵のまま使え、書き換えた文は検証に落ちた
6. 実機の認証器・パスキーの同期・QR 経由のパスキー・Safari は試せていない（#343 の §2.3 と同じ制約）

## 3. 何を暗号化し、何を平文に残すか

§0 の推薦（案 A）を前提にする。どの案でも、暗号化するものと平文に残すものは同じ。行番号は 2026-10-07 の main（`0d154f0`）。

**粒度: 記録ごとに暗号化する（旅程全体を 1 つの暗号文にしない）。** 今の Host は、役割ごとにどの部分を変えてよいかを操作の種類で決めている（参加者は提案・コメント・思い出の追加と、許されていればチェックだけ。予定・準備リスト・メモ・予算は owner・編集者だけ。`src/cloud-host.ts:770-772`）。旅程全体を 1 つの暗号文にしてブラウザが丸ごと置き換えると、Host は参加者が予定を書き換えたことを見分けられない。予定 1 件・投稿 1 件・準備リスト 1 行などを 1 つの記録にし、記録の id・種類・だれが書いたか（席）を平文で残せば、Host は今と同じ役割の検査を続けられる。中身は分からないまま、どの記録を足し・替え・消したかで判断する。

**暗号文の形**: 個人メモ（`src/private-entries.ts:13-19`）の `v1.` ＋ base64url（IV 12 バイト＋AES-GCM の出力）に、旅行の鍵の世代を足した `v1.<世代>.…`（個人メモの `unpack` の正規表現には通らないので、読む関数は世代を読むように広げる）。鍵は旅行の鍵（§2.1）。追加認証データ（AAD）は `<カプセルの id>/<記録の種類>/<記録の id>/<欄>`（個人メモの `aadOf`、`src/private-entries.ts:49` と同じ考え方）。運用者が暗号文を別の旅行・別の記録・別の欄に入れ替えると開けなくなる。**個人メモと違い、予定の日付・時刻は AAD に入れない**: Host が並べ替え・追加のときに時刻を書き換える（`retime`、`src/cloud-host.ts:791`、`:813`）ので、入れると Host が動かした予定をだれも開けなくなる。そのため運用者は予定の日付・時刻を気づかれずに書き換えられる（中身は読めない）。同じ記録を古い暗号文に戻すこと（巻き戻し）、記録を消すことも見つけられない（個人メモと同じ。`docs/design/private-entries-e2e.md` §1 の末尾）。

**容量**: 暗号文は平文のおよそ 4/3（base64url）＋記録ごとに 28 バイト（符号化の前。base64url の文字と `v1.<世代>.` を足すと、記録ごとにおよそ 45 文字）。カプセルの上限 1,900,000 バイト（`src/cloud-host.ts:490`、`:828`）は変えないので、置ける旅程は今のおよそ 7 割になる。今の上限は Spec と Document の JSON で 2 MiB（`src/schema.ts:68`）だが、実際には 1.9 MB で先に断られている。暗号化の後の文言は実装の PBI で確かめる。

### 3.2 実装の形（#691）

## 5. 平文で置かれている旅行を移す

prod には平文の旅行がある（#480 の足あとを含む）。移すのは 1 回で、平文を読み続ける互換の層は置かない（#526 の設計チェック）。

**だれが・いつ**: その旅行の owner のブラウザが、新しい画面で旅行を初めて開いたとき。旅行の鍵を作り（§2.2 と同じ道）、`spec` の暗号化する部分・`document`・`previous`・足あと・名前を §3 の形で暗号化して、1 回の要求で置き直す。Host は同じ保存（版の CAS、`src/aws-store.ts:23-33`）で平文を消す。保存は meta と最大 16 個の chunk を 1 つのトランザクションで書き、使わない chunk を消すので、平文の古い版は表に残らない（表にポイントインタイムリカバリは無い。`aws/template.yaml:33-54`）。個人メモ（`private`）はもう暗号化してあるので触らない。置き直しは owner の大事な操作として扱い、パスキーの確認を求める（`verified`、`src/cloud-host.ts:178`）。パスキーの無い owner には、今の大事な操作と同じく、その場で登録を求める（`src/client.ts:150-152`）。WebAuthn の無いブラウザでは移せないので、旅行は平文のまま置き、別のブラウザで開くよう案内する。

**大きな旅行**: 暗号文は平文のおよそ 4/3 なので、カプセルの上限（1,900,000 バイト）のまま置き直すと、平文でおよそ 1.4 MB を超える旅行は 413 で断られうる（全体が 4/3 になるとした見積もり。増えるのは暗号化する欄だけなので、実際はもう少し大きい旅行まで入る）。そのときは先に `previous`（元に戻す 1 つ前）を捨てて置き直し、それでも入らなければ平文のまま置いて、owner の画面に「旅程が大きすぎて移せません。予定や投稿を減らしてください」と出す。

**新しい画面を配った後に発行された旅行**は、平文のまま使えないようにする（移せない大きさの旅行は作らせず、owner が席を取ったら移すまで開けない）。WebAuthn の無いブラウザや大きすぎて移せないときに平文のまま使えると、平文で使われる旅行がいつまでも増え、平文の道を消せなくなるため。上の「WebAuthn の無いブラウザ」と「大きな旅行」で平文のまま使えるのは、配る前に発行された旅行だけ。「配った後」の線は Host の設定 `CAPSULE_SEALED_FROM`（テンプレートのパラメータ `SealedFrom`。画面を配り終えた時刻）で、`created` がそれ以後の平文の旅行を「配った後に発行された旅行」とし（`CloudHost.mustSeal`）、owner が移すための操作（読む・鍵・パスキー・`GET` / `POST seal`・`GET grants`）とログアウト・削除のほかは（通す操作の一覧は `src/cloud-host.ts` の `mustSeal` の検査） 409「オーナーがこの旅行を移すまで開けません」を返す。空なら扱いを始めていない（dev は普段は空のまま）。下の「配る前 / 配った後に発行された」は `created` と `SealedFrom` の前後、「扱いを始める前 / 後」は `SealedFrom` を設定する前 / 後のことで、同じ線を指す。発行の上限は線と関係なく 1,200,000 バイトに下げた（暗号化しておよそ 4/3 でも 1,900,000 に入る）。新しい画面は要求にクエリ `ui=2` を付け、印の無い要求が暗号化した旅行・配った後の平文の旅行に来たら 409「画面を更新してください」（#694）。

**移す要求の形**（#694）: owner のブラウザは `GET ""`・`GET seal`（平文の旅行の owner だけに `previous` を返す）・`GET grants` で読み、`src/trip-keys.ts` の `sealMove` で旅程・`previous`・足あとの位置と `by`・全部の席と招待の名前（Host の付けた「自分用」「招待リンク」の招待の名前は平文のまま）を暗号化して、`POST seal` 1 回で送る。読んだ後に増えた・消えた足あと・席・招待があれば 409（「…もう一度移してください」。画面は 1 回だけ読み直す）。暗号化の前の履歴（`audit`）の行は招待・席の id を持たないので、名前（`label` と、「発行者」「作成者」以外の `by`）を暗号化せずに消す。

**移すまでの扱い**:

- 新しい画面は、平文の旅行を今と同じように読み書きする（Host の今の道をそのまま使う）。owner 以外のメンバーには「オーナーが開くと、この旅行は運用者にも読めない形になります」と出す
- owner の画面には、開いたときに「この旅行を、メンバーにだけ読める形に移します」と出し、パスキーの確認の後に移す。移した後、他のメンバーは鍵を受け取るまで読めない（§2.1 の確認コード）。owner の画面に「鍵を待っているメンバー」が並ぶ
- 移すときにオフラインの人・まだ鍵を受け取っていない人がいても、移すのは止めない。読めない間、その人の画面は「オーナーかメンバーから鍵を受け取ってください」を出す
- **owner が来ない旅行**: 削除期限まで平文のまま置く。削除期限は作成から 180 日以内（`src/schema.ts:65`）なので、配る前に発行された旅行は、移せなかったものも含めて、配った後の扱いを始めてから最長 180 日でなくなる。その後に、平文の旅行を平文のまま読み書きする道を Host から消す（§6 の最後の PBI）。配った後に発行された旅行は平文で使われない（上の段落）ので、消す時期を延ばさない。発行と owner が初めに暗号化する道（§2.2）は残す。期限を決めて平文の旅行を読むだけにする案は採らない（§7）
- owner の席が引き換えられていない旅行（作成者・CLI の発行の直後。§2.2）も同じく平文で、owner が席を取ったときに移す。owner が席を取らなければ、削除期限か `/recover` で出し直した招待が引き換えられるまで平文のまま

**API を直前の画面と互換に保つ順番**（CLAUDE.md の互換の前提、`docs/development-and-release.md` の A-4 と B。S3 の画面と Lambda の更新は原子的でない）:

1. Host だけを配る: 平文の旅行は今の API のまま、暗号化した旅行の API（記録ごとの操作、鍵の受け渡し、置き直し）を足す。この時点で暗号化した旅行は 1 つも無いので、直前の画面はそのまま動く。`Spec` の `schemaVersion` は 1 のまま（平文の部分の形は変えない。暗号化したかはカプセルの欄で区別する）
2. 画面を配る: 新しい画面が owner に移す流れを出す。古い画面が暗号化した旅行を開いたら、Host は「画面を更新してください」を返す（古い画面は暗号文を描けない）。配り終えたら、上の「配った後に発行された旅行」の扱いを Host で始める（`SealedFrom` を置く。置いた後も `aws/verify.ts` は配置の smoke test として通る。#893 で済んだ）
3. 2 の扱いを始めてから 180 日が過ぎたら（配る前に発行された旅行が全部、削除期限を過ぎる）、平文の旅行を平文のまま読み書きする道を Host から消す。消す前に、運用者の一覧（`src/cloud-host.ts:463`）で、配る前に発行された平文の旅行が残っていないことを確かめる（§6 の 6）

## 8. 鍵を替える（#695）

§2.1 の「実装の PBI で決めること」と、§2.3 の表 3 の「owner の招待の交換」で残した「どう防ぐか」を、#695 で決めた。部品は `src/trip-keys.ts`（`reachableSeats`・`signRekey`・`verifyRekey`・`acceptRekey`・`signSuccession`・`resealAll`）で、画面・Host のテスト・`aws/verify.ts` が同じ関数を使い、Host は呼ばない。

1. **新しい世代の鍵の出どころ**: owner のブラウザが世代 n+1 の旅行の鍵を作り、席ごとの包み（`wrapped`・`ephemeral`）に owner の席の Ed25519 で署名する（`capsule rekey v1/<capsule id>/<世代>/<席>/<席の X25519>/<wrapped>/<ephemeral>`）。メンバーのブラウザは、前に受け取った世代より新しい包みを、署名した席が owner で、自分の辺からその席にたどれ（`reachableSeats`。たどり始めるのは、この端末が持つ自分の席の公開鍵からで、Host の一覧に載った自分の公開鍵ではない）、署名が通るときだけ開く（`acceptRekey`）。運用者が owner の席を作っても（`/recover`）、だれかがその席と確認コードを合わせるまで辺が無いので、その席の置いた世代は受け取られない。古い世代の鍵で新しい鍵を包む鎖は作らない（抜けた人は古い鍵を持つので、運用者と組めば防げない。§2.1 の限界。運用者だけなら owner の署名で足りる）
2. **抜けた席の記録**: Host が、今の世代の鍵を持つ席が抜けたときに `Capsule.departed` に席の id と理由（`revoke`・`rotate`・`expired`・`owner`）を置き、owner の `GET` に替える印（`auto`・`ask`）を返す。抜ける理由ごとの扱いは §2.3 の表 3 のとおり（替える: メンバーの失効、owner 以外の招待の交換・引き換え済みの招待の失効、削除期限より短い招待の期限 / 聞く: owner の招待の交換、`/recover` / 記録しない: 共有の終了、古い世代の鍵だけを持つ席）。owner のブラウザが鍵を替えると消え、「替えない」を選ぶと `ask` の行だけ消える
3. **後からパスキーを登録した席**: 鍵の組を作り直し、前の Ed25519 で新しい公開鍵に署名した `since`（前の X25519・Ed25519 と署名）を置き、自分から出る辺は新しい鍵で署名し直す。他の席の辺は前の公開鍵に署名したままでも `since` を通ってたどれる。`since` は 1 代だけで、2 回作り直した席は辺が切れ、次の鍵の交換で確認コードからやり直す（パスキーの登録・置き換えはまれ）
4. **owner の招待の交換**: 暗号化した旅行で、owner のほかに今の世代の鍵を持つ席が無ければ、Host が 409 で断り、画面も押す前に止める（「鍵を持つメンバーが他にいないため、交換すると旅程をだれも読めなくなります。先に別の端末かメンバーに鍵を渡してください」）。「新しい owner が鍵を受け取ってから古い席を消す順番」は採らない: 失効の後も古い owner の席を残す状態が要り、`session()` の検査が増える。ひとりの旅行の owner が端末を替えるときは、同期したパスキーで戻るか、先に別の端末を編集者などで招いて鍵を渡す。`/recover` は運用者の操作なので止められず、§2.3 の表 2 のとおり鍵を持つメンバーがいなければ読めなくなる
5. **`previous`**: 鍵を替えると消える（暗号文の写しを新しい世代で作り直さない。暗号化した旅行の元に戻すは #707 で使えない）。替えた後は、Host が今の世代でない暗号文の書き込みを断る（抜けた人が読める古い世代の暗号文を増やさない）
