# Ephemeral Trip Capsule — 期限付き旅程共有アプリ

## 0. 概要

Capsule Host は、旅行ごとに形を変えられる **期限付きの旅程カプセル**を同行者と共有するアプリである。旅行ごとのアプリを作るのではなく、1 つの共通ランタイムが旅行ごとの宣言（`TripAppSpec`）を解釈して画面を出す。

利用者は自然言語で欲しい旅程を伝える。LLM は任意コードではなく、共通ランタイムが解釈する `TripAppSpec` を生成する。カプセルには最初から終了日があり、参加者はアカウントを作らず、権限の異なるリンクで入る。旅行後は追記期間を経て読み取り専用になり、Markdown などへ書き出した後に消える。

```text
prompt
  → TripAppSpec 生成
  → ローカル preview / schema 検査
  → 公開承認
  → 期限付きリンクを共有
  → 旅行中に共同利用
  → 思い出を追記
  → freeze / export
  → revoke / purge
```

旅行ごとに別の Web アプリ、依存関係、DB、デプロイ先は持たない。サーバー側は 1 つの共通ランタイムとマルチテナントのデータストアだけで動く。

## 1. 旅程用 AppSpec

### 1.1 設計原則

`TripAppSpec` は「どんな画面と操作を提供するか」を宣言する。旅行中の実データとは分離する。

- **Spec**: タイトル、期間、タイムゾーン、表示モジュール、テーマ、権限、出力形式。比較的変更が少ない。
- **Document**: 日ごとの予定、候補、チェック項目、コメント、旅行後のメモ。利用中に更新される。
- **Runtime**: Spec を検証・描画し、許可された操作だけを API に変換する共通コード。

LLM が生成できるのは Spec と初期 Document までとし、JavaScript、HTML、任意 CSS、SQL、外部スクリプトは生成・実行しない（**生成物の範囲**の話。生成を誰が動かすかは §1.5）。カスタマイズは用意された部品、レイアウト、テーマトークン、文言の組み合わせで行う。

### 1.2 最小スキーマ

旅程は Domain Kit の 1 つ（`kind: "trip"`、`src/trip-kit.ts`）。Host が種類によらず読むのは `kind`・`title`・`lifecycle.purgeAt` と Document の `revision` だけで、ほかの種類のアプリの足し方は [Domain Kit](domain-kit.md)。

```ts
type TripAppSpec = {
  schemaVersion: 1;
  kind: "trip";
  title: string;
  summary?: string;
  locale: "ja" | "en";
  timezone: string;             // 旅程の基準。各項目は必要なら別 timezone を持てる
  trip: {
    startsOn: string;           // YYYY-MM-DD
    endsOn: string;
    destinations: string[];
  };
  modules: ModuleSpec[];
  navigation: string[];         // module id の順序
  theme: {
    preset: "paper" | "postcard" | "minimal" | "night";
    accent: string;             // 許可された色形式のみ
    cover?: { kind: "gradient" | "preset-image"; value: string };
  };
  collaboration: {
    participantSuggestions: boolean;
    participantComments: boolean;
    participantChecklist: boolean;
  };
  lifecycle: {
    reflectionDays: number;     // 旅行終了後の追記期間。既定 7、最大 30
    purgeAt: string;            // 絶対日時。作成から最大 180 日
  };
  exports: Array<"markdown" | "json" | "ics" | "html">;
};

type ModuleSpec =
  | { id: string; kind: "day-timeline"; label: string }
  | { id: string; kind: "places"; label: string; groupBy?: "area" | "category" }
  | { id: string; kind: "suggestion-board"; label: string }
  | { id: string; kind: "checklist"; label: string; mode: "shared" | "per-participant" }
  | { id: string; kind: "budget"; label: string; currency: string }
  | { id: string; kind: "notes"; label: string }
  | { id: string; kind: "reflection"; label: string }
  | { id: string; kind: "moments"; label: string };     // 写真のページ（§1.3「写真」）
```

`navigation` に含まれないモジュールは描画しない。同じ Runtime でも、「時刻中心の出張」「場所候補を皆で決める旅行」「チェックリスト中心のキャンプ」のようにかなり異なるアプリを生成できる。

### 1.3 旅程データ

中心となる `ItineraryItem` は、交通・宿泊・活動などを同じ時系列に置ける形にする。

```ts
type ItineraryItem = {
  id: string;
  kind: "transport" | "stay" | "activity" | "meal" | "note";
  status: "proposed" | "confirmed" | "cancelled";
  title: string;
  startsAt?: string;            // 新しく発行する旅程では必須（発行済みの旅程には無い予定がある）
  timeTentative?: boolean;      // Host が置いた・まだ決まっていない仮の時刻（画面では「10:30 ごろ」）
  endsAt?: string;              // 任意。画面の「編集」で入れる（開始を変えると同じだけずれる）。後の予定との重なり・空きは表示だけで、他の予定は動かさない
  timezone?: string;
  place?: {
    label: string;
    address?: string;
    publicUrl?: string;
    lat?: number;               // 任意。十進の度（WGS84、-90〜90）。lng とそろえる。チャットの LLM が付け、足あとの地図に予定の印で出る
    lng?: number;               // 任意。-180〜180
  };
  description?: string;         // sanitise 済み Markdown
  tags?: string[];
  revision: number;
};
```

予定の追加・変更は `PATCH document` の `item` 操作。新しい予定は時刻の合う位置に入る。任意の `after`（同じ日の予定の ID）を付けると、その予定の直後に入り、開始時刻は Host が前後に合わせる（収まっていれば送った時刻のまま、収まらなければ仮置きの時刻にして `moved` で返す。`move` と同じ規則）。画面の予定と予定の間の「＋」がこれを使う。`after` の予定が無い・別の日・既にある予定の ID なら 400。

画面（`src/client.ts`）の旅程は日ごとのタブで、その日の予定を「詳細」（時刻・状態・メモ・地図リンクのカード）と「リスト」（時刻と題だけ、1 件 1 行）で切り替えて見る（選んだ表示はそのブラウザが覚える）。owner / editor は、予定の持ち手（⠿）をドラッグするか、持ち手にフォーカスして上下の矢印キーで、同じ日の中の順番を入れ替える（`move`）。動かした予定の開始時刻は Host が置いた位置の前後に合わせ（前の予定の終了、終了が無ければ前の予定の開始の 1 時間後など。前後の間に収まっていればそのまま）、変えたときは画面に「〇〇を 10:30 ごろ に変えました」と出す。Host が決めた時刻は仮置き（`timeTentative`）で、画面と書き出しでは「10:30 ごろ」と出す。「編集」の開始時刻は必須で、仮置きかどうかをチェックで選ぶ（時刻を変えるとチェックは外れる）。別の日へ移すには「編集」で日付を変える。終了時刻があれば「10:30 – 12:00」と出し、「編集」で開始を変えると終了も同じだけずれる（ずらした終了が日をまたぐときは終了を空にする）。同じ日のそれより前の予定のうち最も遅い終了と、その予定の開始から、空き（「空き 45 分」）と重なり（「前の予定と重なっています」）を出す（知らせるだけで、他の予定は動かさない）。候補から旅程に足した予定は、その日の最後に仮置きの時刻で入る。

準備リストと費用メモは、`PATCH document` の `checklist` / `budget` 操作で一覧を丸ごと置き換える（owner / editor だけ。画面の「準備リストを編集」「費用メモを編集」が使う）。項目ごとの追加・変更・削除の操作は無い。同時に書き込まれても `If-Match` の版の一致で後から来た方が 409 になるので、片方の変更が黙って消えることはない。チェックの状態は同じ ID の項目に残り、新しい項目は未チェックで入る。

参加者の候補は `Suggestion` として `ItineraryItem` から分ける。候補を確定旅程へ昇格できるのは owner/editor だけにする。これにより、参加者の気軽な提案と正式な旅程が混ざらない。候補は旅行記（エクスポートの Markdown / HTML）にも「候補」として載る。相談（`comments`）は決めたいこと・質問・ひとことの置き場で、旅程にも旅行記にも入らない（JSON で書き出すときの `trip.json` には残る）。画面の候補・相談タブも、2 つの見出しの下にこの違いを短い説明で 1 つずつ書いている。owner / editor は投稿 1 件の本文を直し（`PATCH document` の `rewrite`）、投稿を消せる（`remove`。どちらも `list: "suggestions" | "comments"` と投稿の ID で指す）。消した候補は旅行記にも載らず、旅程に追加済みの予定は残る。誰が出した投稿かは記録しないので、投稿した本人だけが直す仕組みは無い。

#### 個人用の予定・日記

メンバーは役割を問わず、自分だけの予定（日付・開始時刻・題・本文）と日ごとの日記を書ける。置き場所は `document` の外、カプセルの payload の `private` に席（`Session.id`）ごとの一覧で、1 席 100 件まで。題・本文・場所はブラウザが暗号化してから送り、Host の運用者にも読めない（§1.4 の「運用者にも読めないもの」）。本文 4000 字・題 160 字の上限は画面が暗号化の前に見て、Host は暗号文の形と長さだけを見る。容量はカプセル全体の 2 MiB を共有で使う。

- `GET /v1/c/:id` は呼んだ席の分だけを `private` で返す。他の席の分はどの役割にも返らない
- 書くのは `PATCH /v1/c/:id/private`（`{ type: "put", entry }` で追加・置き換え、`{ type: "remove", id }` で削除、`{ type: "apply", put, remove }` で何件もまとめて、`{ type: "key", wrapped }` で席の鍵を 1 回だけ置く）。`apply` は全部を検査してから 1 回で書き換え、1 件でも通らなければ何も変えない。鍵の無い席は `put` できず（400）、`remove` はできる。`If-Match` は要らず、`document.revision` も `ETag` も進めない（他のメンバーの画面に「更新あり」として出ない）。日付は旅行期間の中だけ。`createdAt` / `updatedAt` は Host の時計で書く。旅行後（reflection）も書け、共有終了（frozen）の後は 403
- Host が日付 → 開始時刻 → 書いた順に並べ、画面は日のタブで共有の予定の間に時刻で混ぜて「自分だけ」の印を付ける（空き・重なりの計算と並べ替えには入れない）。日記はその日の「自分の日記」に書いた順で出る
- チャットでも直せる。日記カードの「チャットで直す」で、ブラウザが直し方（`docs/recipes/private.md`）・旅行期間と時間帯・共有の予定の日付・時刻・題（参考。直しても反映されない）・自分の読めた分の JSON を組み立ててコピーする。他のメンバーの分は入らない。チャットの返事を貼ると、ブラウザが取り出して検査し（`src/private-revise.ts`）、追加・変更・削除の差分を見せる。反映すると全件をブラウザで暗号化して `apply` を 1 回送る（全件か 0 件）。この端末で読めない分はコピーに入らず、件数を画面に出し、反映しても消えない。返事が今の一覧に無い id を名指ししても上書きせず、新しい項目として足す
- 本人の分だけを Markdown で持ち出せる。画面の日記カードの「自分のメモを保存 ↓」で、ブラウザが自分の読めた分から作ってダウンロードさせる（Host は Markdown を作らない。`GET /v1/c/:id/private.md` のようなルートは無い）
- 席が消えると（メンバーや招待の失効、共有終了、期限切れ）その席の個人メモも次の保存で消える。パスキーで同じ席に戻ったブラウザは `Session.id` が変わらないのでそのまま読める

更新は `revision` と `If-Match` による楽観ロックを使う。WebSocket のリアルタイム同期は行わず、更新後の再取得と短いポーリングで済ませる（旅行用途の編集頻度なら、常時接続・競合処理・運用監視を減らせる）。

個人予定・個人日記は試験機能として、旅程の追加入口・詳細/リストの個人予定・思い出の日記・個人用チャット修正入口に表示する。登録・編集画面と個人用チャット画面では、入力やコピーの前に「試験機能です。機微な情報は入力しないでください。」を案内する。

#### 写真

メンバーは旅行中の写真を上げ、同行者みんなが日ごと・撮影日時の順に見られる。Spec の `moments` のページ（テンプレートでは「写真」、`days` の後）がそれで、`label` のほかに設定は無い。置き場所は 2 つに分かれる: 写真の情報は `document` の外、カプセルの payload の `media`（旅行で 1 本の一覧、上げた順）。画像本体（表示用とサムネイルの 2 つ）は構造化データと別の置き場（`MediaStore`。ローカルは `<データ置き場>/media/<行のキー>/`、AWS は非公開の S3 `Media`。`aws/README.md` の「写真の置き場」）で、**画像も位置も一言も、ブラウザが旅行の鍵で暗号化してから上げる**。Host は中身を開かず、運用者にも読めない。暗号化の方式・平文と暗号文の分け方は §5.2・§5.3・§5.5 を正とし、ここには写真に固有のことだけを書く。

- **既定では無効**: 運用者が環境変数 `CAPSULE_PHOTOS=1`（AWS はスタックのパラメータ `Photos`）にするまで、`POST media` は 403「写真は今は使えません」で、`GET /v1/c/:id` は `photos: false` を返し、画面は写真のページを出さない。すでにある写真の閲覧・削除と、旅行の削除での画像の削除は、無効にしても動く
- 1 枚の情報（`PhotoAsset`、`src/media.ts`）: `id`（ブラウザが作る 32 桁の 16 進）、`contributor`（上げた席。Host の中だけで、画面には自分の写真かどうか `mine` だけ返す）、`uploadedAt`（Host の時計）、`capturedAt`（EXIF の撮影日時。オフセット付きの時刻だけ。**平文**）、`width`・`height`・`thumb`（サムネイルの寸法。平文）、`itineraryItemId`（上げた本人・owner・editor が手で選んだ予定の id。平文。時刻での紐付けの結果は入れない）、`blob`（Host が付ける画像の名前。平文）、`key`・`location`・`caption`（**旅行の鍵の暗号文**）。`key` は 2 つの画像を封じた写真ごとの鍵で、鍵を替える（§8）ときはこの短い文字列だけを封じ直し、画像は取り出して送り返さない。画像は `blob` の名前で置き、別のアップロードが確定した写真の bytes を上書きしない。確定しなかったアップロード（失敗・容量超え・競合で負けた・削除と重なった）は自分が置いた画像を取り除く
- 上げる: `POST /v1/c/:id/media`（本文は `{ id, images: { display, thumb }, width, height, thumb, capturedAt?, key, location?, caption? }`。`images` は暗号文（IV 12 バイト + 封じた bytes + タグ 16 バイト）の base64。1 回の POST で 1 枚、本文は今の 2 MiB の上限のまま）。上げられるのは owner・editor・participant で、閲覧者（viewer）は 403。旅行前・旅行中・旅行後（reflection）に上げられ、共有終了（frozen）の後は 403（見るのは今どおり）。暗号化していない旅行（平文の旅行）には上げられない（409。画像を封じる鍵が無い）。1 旅行 500 枚まで・表示用の暗号文は 1 MiB・サムネイルは 150 KiB まで（どれも暗号化の分の 28 バイトを足した大きさ）を越えれば 413 と日本語の理由、寸法が長辺 2048px（サムネイルは 400px）を越える・`capturedAt` がオフセット（`Z` か `±hh:mm`）の無い時刻・`location` や `key` が旅行の鍵の暗号文の形でない（平文）ときは 400、`id` が重なれば 409。1 席 1 分 60 枚まで
- 見る: `GET /v1/c/:id` がどの役割にも `media`（上の情報から `contributor`・`blob` を除き `mine` を足したもの）を返し、`GET /v1/c/:id/media/<id>/(thumb|display)` が席のある人なら役割を問わず暗号文をそのまま返す（`application/octet-stream`、`Cache-Control: private, max-age=3600`。無い写真は 404、席の無い・失効した・別の旅行の Cookie は 401）。画像の読み取りは、写真のページが数百枚を一度に読むので、通常の回数制限（アドレスごと毎分 300・招待ごと毎分 120・旅行ごと毎分 600）に数えず、席ごと毎分 600・アドレスごと毎分 1,200 で数える。`document.revision` も `ETag` も進めず、カプセルの変更履歴にも積まず、書き出し・「チャットで直す」には入らない
- 消す: `PATCH /v1/c/:id/media` の `{ type: "remove", id }`。上げた席の本人と owner・editor。他の席は 403、共有終了の後は 403。席が消えても（メンバーや招待の失効、共有終了）写真は旅行の写真として残る
- 画面（`src/client.ts` の `photosPage`）: 写真を選ぶと、ブラウザが元の写真の EXIF から撮影日時と位置を読み（`readExif`。**EXIF に無ければ付けない**。ファイルの更新時刻・端末の今の位置では補わない。日時の無い写真は「時刻の分からない写真」に入る）、向きを直して表示用（長辺 2048px・1 MiB まで）とサムネイル（長辺 400px）の JPEG に描き直し（描き直しで EXIF・GPS・XMP・コメントは付かない）、`inspectJpeg` でもう一度メタデータの区画を落として形・寸法・大きさを調べ、画像と位置を暗号化して上げる。見る側のブラウザは、サムネイルを画面に入ったときに取り、復号し、もう一度 `inspectJpeg` を通してから `blob:` の URL で出す（悪いメンバーが EXIF 付きや JPEG でないものを上げても広がらない。CSP の `img-src` に `blob:`）。開くと表示用の画像と撮影日時（と、位置があれば地図リンク）と一言が出て、上げた本人と owner・editor には載せる予定と一言を直すフォームと「消す」が出る（2 回押す）。写真の位置は画像から消えて、暗号化した写真の情報にだけ残り、旅行の削除と一緒に消える
- 位置は端末と OS が決める: iPhone は写真を選ぶ画面で位置情報を含めたときだけ、Android のブラウザから上げた写真には付かない（Android が位置を隠して渡す）。カメラで撮って直接渡した写真は日時も付かないことがある
- 削除: オーナーの完全削除・運用者の terminate・期限の削除（sweep）は、行を空にする前にその旅行の画像をすべて消す（消せなければ行を残して次の sweep でやり直す）。AWS の S3 `Media` には、作成から 181 日で消える規則を最後の歯止めに付ける（旅行は作成から 180 日までなので、消し漏れがあっても 181 日で消える）。削除の正は Host（§3.3）
- 運用者に残るのは、写真の件数・撮影時刻・だれの（席の）ものか・寸法・暗号文の長さ・上げた時刻だけ（§5.2 の「運用者に残るもの」）。原本（元のままの写真）は持たず、表示用とサムネイルだけを置く。動画・Live Photo・HEIC のままの保存はしない
- 予定の下に並べる（`src/moments.ts` の `linkPhotos`）: 写真は、撮影した日（旅行のタイムゾーンで数える）の中止でない予定のうち、開始時刻が撮影時刻以前で最も遅いもの（同じ時刻に始まる予定が 2 つあれば旅程で後ろの方）に紐付き、日のタブの「詳細」でその予定のカードの下にサムネイルが撮影時刻の順に並ぶ（一言があれば添える）。「リスト」では写真の付いた予定の行に枚数（📷 3）が出る。その日の最初の予定より前に撮った写真は日の先頭の「予定の前」に、撮影日時の無い写真・旅行期間の外の写真は写真のページの「時刻の分からない写真」にだけ出る。紐付けは画面が描くたびに求め、旅程（`document.items`）にも `media` にも書き戻さない。自分だけの予定には付かない
- 選び直しと一言: 上げた本人と owner・editor は、写真を開いて載せる予定を選び直せる（`PATCH /v1/c/:id/media` の `{ type: "link", id, itemId }`。`itemId: null` で撮影時刻の紐付けに戻す。旅程に無い予定は 400「予定が見つかりません」）。一言も付けられる（`{ type: "caption", id, caption }`。旅行の鍵の暗号文で、`null` で消す。160 字は書くブラウザが確かめ、Host は暗号文の形と鍵の世代だけを見る）。他の席・閲覧者は 403「自分の写真だけ直せます」、共有終了の後は 403。応答は `{ photo }`。`document.revision` も `ETag` も進めず、変更履歴にも積まない。選び直した写真は `itineraryItemId` を持ち、その予定の日・時刻・状態が変わっても付いたまま。予定が旅程から消えると（「チャットで直す」・1 つ前に戻す・編集のどれでも）、Host が保存の前に `itineraryItemId` を外し、撮影時刻の紐付けに戻る
- 足あとから位置（`src/moments.ts` の `photoPlace`）: 位置の無い写真で撮影日時のあるものは、撮影時刻にいちばん近い足あとの点（前後 30 分以内。メンバーのだれの点でも。同じ近さなら先の点）の位置を、写真を開いたときの「撮影した場所を地図で見る（近くの足あとから）」に使う。写真に位置があればそちらを使う。画面が開くたびに求め、Host には書き戻さない
- 旅を再生する・写真付きの ZIP は無い

#### 足あと

旅行中に「ここにいる」を押すと、その時刻と場所が旅の足あととして残り、メンバー全員が見返せる。置き場所は `document` の外、カプセルの payload の `footprints`（旅行で 1 本の一覧、古い順）。1 点は `{ id, seat, by, at, lat, lng, accuracy, auto? }` で、`at` は Host の時計、`lat` / `lng` / `accuracy`（メートル）はブラウザの位置（Geolocation API）を 1 回取ったもの、`seat` は残した席（`Session.id`）、`by` はそのときの席の表示名（「オーナー」「メンバーN」、owner が付け替えた名前）、`auto` は開いたときに自動で残した点だけ `true`（押した点には無い）。

- 残す: `PATCH /v1/c/:id/footprints` の `{ type: "add", lat, lng, accuracy }`（自動で残すときは `auto: true` を足す。期間・件数・1 分の上限・精度の規則は押したときと同じ）。閲覧者（viewer）は 403。旅行期間中（active で、旅行のタイムゾーンの今日が開始日〜終了日）だけで、その外・旅行後（reflection）・共有終了（frozen）は 403。1 旅行 1000 件まで（400）、1 席 1 分に 1 回まで（その席の残っている最後の点から数える。429）。精度が 1 km（1000 m）より悪い点は Host も 400 で断り、画面は送る前に理由を出す
- 消す: `{ type: "remove", id }`。残した席の本人と owner / editor。他の席の点は 403、共有終了の後は 403
- 見る: `GET /v1/c/:id` がどの役割にも `footprints` を返す（`seat` は返さず、呼んだ席の点かどうかを `mine` で、自動で残した点かどうかを `auto` で返す）。`If-Match` は要らず、`document.revision` も `ETag` も進めない。書き出し（ZIP・Markdown・旅程のページ）と「チャットで直す」には入らない。カプセルの変更履歴（招待の履歴）にも積まない
- 画面: 足あとのページは 1 つで、Spec の `trip-map` のページ（テンプレートでは「足あとの地図」）がそれ。「ここにいる」と「開いたときに足あとを残す」を地図の上に、地図の下に日ごと・時刻順にだれ・時刻・地図リンク・「消す」を並べ、自動で残した点には時刻の後に「自動」と出す。Spec の navigation に `trip-map` のページが無い旅行（足あとの地図のページができる前に作ったもの）だけ、画面が「足あと」のページ（`:footprints`）を足して同じものを出す（思い出のタブを補うのと同じく、保存済みの Spec は変えない）
- 位置の許可: ブラウザが `<geolocation>` 要素を持つとき（Chrome）、足あとのページの「ここにいる」はその要素で、位置を拒んだあとも画面の位置のボタンを押せば許可し直せる（案内も「位置のボタンを押して許可し直す」）。要素が渡す位置は押したときと同じ処理（精度 1 km、保存）に通す。要素を持たないブラウザは今のボタンとサイト設定の案内のまま。開いたときに自動で残す足あとは、要素を使わず、許可が無ければ位置を求めない。Host の API・ヘッダは変えない
- 開いたときに自動で残す: 足あとのページ（地図のページ）の「開いたときに足あとを残す」を本人がオンにした端末だけ（既定はオフ。旅行ごとにその端末のブラウザ（`localStorage`）に持ち、Host には置かない）。旅行のページを開いた時と画面に戻った時（`visibilitychange` で見えるようになった時）に、位置を 1 回取り、前の自分の点（押した点も自動の点も）から 15 分以上たったか 300 m 以上離れていれば `auto: true` で 1 点残す（`src/footprints.ts` の `AUTO_FOOTPRINT`）。旅行期間中だけ（Host の 403 と同じ）。位置の許可を求めるのはオンにした時だけで、開いた時は許可済みのときだけ位置を取る。許可が無い・精度が 1 km より悪い・Host が断った（403 / 429）ときは何も残さず、何も言わない（押した人がいないため）
- 位置を見張り続ける・画面が裏にある間や閉じている間に残すことはしない（§4）
- 足あとの地図: Spec の `trip-map` のページ（テンプレートでは「足あとの地図」）は、自分たちの配信元から配る地図データ（PMTiles。日本は z15 まで、ほかは z8 まで）の上に、足あとの点を MapLibre で描く（地図データの出どころと帰属は §5.8）。点は全員の足あとで、日・メンバーで絞れる（絞り込みは地図の下の一覧にも効く）。座標（`place.lat` / `place.lng`）を持つ予定（取り消した予定を除く）は、予定の印（足あとの点と見分けのつく四角）として同じ地図に重なる。印を押すと予定の日付・時刻・題・場所と地図リンクが出る。「予定」「足あと」で出す・出さないを切り替え、日の絞り込みは予定にも効き（日の選択肢は予定と足あとのある日を合わせたもの）、メンバーの絞り込みは足あとにだけ効く。足あとが 0 件でも座標つきの予定があれば地図が出る。切り替えは画面の状態で、保存しない。予定の線は引かない。`showTrack` なら同じメンバーの点を時刻の順に線で結ぶ。線は点を結んだもので、実際に通った道ではない（道路に沿わせない）。前の点から 3 時間以上あく区間と、時速 150 km を超える区間（飛行機・新幹線など。速さは最短 1 分で測る）は線を切る（`src/footprints.ts` の `TRACK_LIMITS`）。座標の小数 4 桁（約 10 m）が同じ点は 1 つの点にし、点を押すと、その点の足あとの時刻・だれ・その時刻の予定（`src/moments.ts` の `itemAt`）・地図リンクが出る。足あとも座標つきの予定も無いときは、地図と一覧の代わりに残し方（「ここにいる」）を出す。`showPhotos` は使わない（v0.25.0 から Recipe が書いた Spec を読むために任意で残している）
- 背景の地図（道路・地名・海岸線）は、自分たちの配信元（Assets バケットの `map/`）に置いた地図データから出す。地図の部品（`map.js`・Worker・スタイル）は足あとのページを開いたときに初めて読み込み、ほかのページは重くしない。CSP は変えていない（Worker は同じ配信元の module、タイルは `connect-src 'self'` の Range 要求）。地図に「© OpenStreetMap contributors」を出し、OpenStreetMap の著作権とライセンスのページ（`https://www.openstreetmap.org/copyright`）へのリンクにする（地図データは ODbL の派生物。別のタブで開くだけ）。外部のタイル配信サービスは、閲覧者のブラウザがタイルを取りに行き、見ている地域と IP が配信元に渡るので使わない。予定の座標は旅程を作る・直すチャットの LLM が付け（Recipe）、Host は地名から位置を引かない（外部のジオコーディング API を使わず、旅行の行き先を外に渡さない）。地図データの作り方と置き場は `aws/README.md` の「足あとの地図の背景（地図データ）」、外部に渡るものは §5.8
- 席が消えても（メンバーや招待の失効、共有終了で owner 以外の席が消える）点は消えず、記録したときの名前で残る。旅行の削除（purge・期限切れ）でカプセルごと消える
- 移した旅行・暗号化して作った旅行では、位置とだれの名前は旅行の鍵の暗号文で、運用者には時刻・席の id・自動で残した点かどうかだけが読める。owner が新しい画面で移していない平文の旅行（配る前に発行されたもの、線の後に発行され移すまで使えないもの）は、移すまで運用者に読める（§1.4）

#### 旅の記録（`story`）

Spec の `story` のページ（テンプレートでは「旅の記録」、`days` の後）は、旅程と足あとを並べて「予定」と「実際」を見返す。日ごとに予定を旅程の順に並べ、その予定の時間帯の最初の足あとの点を「記録」として「予定 12:00 / 記録 13:02」で出す。予定の時間帯は `src/moments.ts` の `itemAt`（写真の紐付けと同じ規則: 同じ日の中止でない予定のうち、開始が点の時刻以前で最も遅いもの）。

- 予定になかったところ: その日の最初の予定より前の点、予定の終了時刻より後の点、同じ予定の最初の点から 2 km 以上（`src/story.ts` の `UNPLANNED_KM`。Spec の設定にしない）離れた点。時刻・だれの点か・地図リンクで、開始がその点より後の最初の予定の前に入る。地名は出さない（座標から地名を引く外部 API が要る）
- 足あとの点の無い予定は時刻と題だけを短く出し、中止の予定は出さない。旅行の日の外の点は出さない。足あとが 1 点も無ければ予定だけを出し、残し方（足あとのページの「ここにいる」）を書く
- 結果は保存せず、画面が描くたびに `src/story.ts` の `story()` で求める。旅程にも足あとにも書き戻さない（計画を実際の時刻で書き換えない）。Host の API は変えない
- 旅行後（`reflection` / `frozen`）に旅行を開くと、`story` のページがあれば最初に出る（§3.1）。旅行中は今どおり `navigation` の先頭。選ぶのは読み込んだ最初の 1 回だけで、タブを押した後の再読込・20 秒ごとの更新では戻さない
- 写真は使わない（写真を並べる・撮影時刻を記録に使うことはしない。写真のページは §1.3「写真」）

### 1.4 保存しない情報

個人データについて、このサービスに保存した題・本文・場所は暗号化され、同行者・オーナー・サービスの運用者には読めない。日付・時刻などは暗号化されない。機微な情報を安心して保管できることを保証するものではなく、入力しないよう案内する。パスキーを失うと本人にも読めなくなる。個人用チャットでコピーした文は外部チャットサービスに渡り、そのサービスには読める。Host 内の暗号化はコピー先を保護しない。

URL を知る人が入れる設計なので、次は入力時に警告し、専用フィールドも用意しない。

- パスポート、本人確認書類、クレジットカード情報
- 航空券や入場券の QR / バーコード
- 予約変更に使える確認番号や秘密 URL
- 自宅住所、鍵の受け渡し情報、健康情報
- API キー、パスワード
- 写真に写った本人確認書類・QR コード・予約の確認画面・他人の顔や住所（写真もカプセルに置かない。旅行の鍵で暗号化して運用者に読めなくしても、同行者全員には見える）

地図は外部 API・タイルを埋め込まない。予定の場所と足あとの 1 点は通常の地図 URL を新しいタブで開き（足あとは緯度経度を検索語にする）、足あとの地図（`trip-map`）は自分たちの配信元に置いた地図データの上に足あとの点を描く（外部のタイル配信サービスは使わず、CSP は変えない。§1.3）。写真は旅の記録として上げられる（§1.3「写真」）。画像本体は旅行の鍵で暗号化して構造化データと別の期限付きの保存先に置き、カプセルの purge と同時に消す。EXIF はブラウザで落とし、撮影日時は平文、位置は暗号化した写真の情報にだけ残す。ファイル（写真以外）のアップロードは持たない。カプセルあたりの JSON データを 2 MiB、写真を 500 枚（1 枚は表示用 1 MiB・サムネイル 150 KiB まで）、参加者を 50 人、変更履歴を 2,000 件までに制限する。

旅程・足あと・メンバーと招待の名前は、旅行の鍵（メンバーのブラウザだけが持つ）の暗号文で置く（§5.2）。DynamoDB を読める運用者に読めるのは、暗号文と平文の部分 — 日付・時刻・件数・全体の大きさ・役割・だれの記録か（席と招待の id）、Host が付けた名前（招待の「自分用」「招待リンク」、席の「オーナー」「メンバーN」と、履歴の「発行者」「作成者」）— だけ。`aws/recover.ts` で出し直した owner 席も、ほかのメンバーから鍵を受け取るまで旅程を読めない。平文で置かれるのは次の間だけ: (1) 発行から owner が席を取って鍵を作り暗号化するまで（受付は 3 日。席を取らなければ削除期限か、`/recover` で出し直した招待が引き換えられるまで）(2) owner がまだ新しい画面で開いて移していない旅行（配る前に発行されたものは移すまで平文のまま使え、「配った後」の線より後に発行されたものは移すまで使えない。どちらも移されなければ削除期限まで平文。§5.4）。**閉じない経路**: 画面の JavaScript は運用者が配る（S3 の `dist/public/`）ので、復号した旅程や旅行の鍵を送り返すコードを配れば読める（§5.3 の「閉じない経路」）。

#### 運用者にも読めないもの（自分だけの予定・日記）

自分だけの予定・日記（§1.3）の題・本文・場所は、ブラウザで暗号化して Host には暗号文だけを置く。DynamoDB を読める運用者も、`/recover` で owner の席を出し直した人も、題・本文・場所は読めない。旅行の鍵との違いは §5.6。

| 項目（`Capsule.private[<Session.id>][]` と `Session`） | 運用者から見て | 理由 |
|---|---|---|
| `title` / `body` / `place`（`place` は `{ label, publicUrl }` を JSON にしてから） | **暗号文**（`v1.` + base64url の IV と AES-GCM の出力） | 内容そのもの |
| `id` / `kind` / `day` / `startsAt` / `endsAt` | 平文 | Host が置き換え・削除の対象を探し、旅行期間の中かを見て、時刻順に並べる |
| `createdAt` / `updatedAt` | 平文 | Host の時計で書く |
| 席ごとの件数、暗号文の長さ（題・本文・場所のおおよその字数）、`place` があるか | 見える | 詰め物はしない |
| `Session.privateKey`（`wrapped`: 包んだメモの鍵、`passkey`: 包んだパスキーの ID） | 見えるが、パスキーが無いと解けない | 端末を替えても同じパスキーで開くため |
| どの席のものか（`Session.id`。その席の `label` / `device` / `lastUsed` は前から `Session` にある） | 見える | 席ごとに置くため |

- **鍵の置き場所**: 席ごとにランダムなメモの鍵（AES-GCM 256）を 1 本作り、その席のパスキーの PRF の出力から HKDF で導いた鍵で包んで `Session.privateKey` に置く。開いた端末は、取り出せない `CryptoKey` として IndexedDB（`capsule` / `private-keys`）に持ち、毎回はパスキーを求めない。書くにはその席のパスキー（PRF の出るもの）が要る
- **端末から消すとき**: そのブラウザで旅行を開いて、席が無くなった 401（`seat: "gone"`）・404・410 が返ったとき、オーナーがそのブラウザで「完全に削除」したとき、トップ画面の一覧に削除予定を過ぎた行があるときに、画面はその旅行についてそのブラウザが置いたもの（IndexedDB の旅行の id のメモの鍵と `seat:<id>` の席の鍵、`localStorage` の `auto-footprint:<id>` と一覧 `capsules` の行）を消す。`seat` の無い 401（30 日使わず切れた cookie、ログアウト、パスキーで戻るを別のブラウザでした）では一覧の行だけ消し、鍵は残す（パスキーで戻れば同じ鍵で読める）。開かれない端末に残ったもの、ブラウザのデータの写し、一覧の 30 件から外れた旅行、Host の `left` に記録の無い席（この記録より前に失効した席など）の失効の 401 では消えない
- **暗号文の入れ替え・書き換え**: 各欄は `<id>/<欄>/<kind>/<day>/<startsAt>/<endsAt>` を追加認証データにして暗号化するので、別の項目・別の欄への入れ替えや、平文の日付・時刻の書き換えは開けなくなる（画面は「この端末では読めません」と出す）
- **失ったとき**: この端末に鍵が無く、パスキーでも開けなければ、その端末では読めない・書けない・消せる。パスキーを失ったら新しい鍵は作らず、続けるには owner に失効と再招待を頼む（席ごと作り直し、古い席の個人メモは消える）
- **チャットに渡したもの**: 「チャットで直す」（§1.3）でコピーした文は、利用者が自分でチャットのサービスに貼るもので、題・本文・場所が平文で入る。そのサービスには読める（運用者に読めないのは Host の中に置いたものだけ）。画面はコピーの前にそう書く。貼り戻した返事も、Host に送るのは暗号化したあとの `apply` だけ
- **防げないもの**: 画面の JavaScript は運用者が配るので、復号した本文を送り返すコードを配れば読める（配る版はコミットと、運用者の配置の記録に残る）。運用者は DynamoDB に書けるので、同じ項目の古い暗号文への巻き戻し・項目や包んだ鍵の削除は防げない（読むことにはならず、壊すことにしかならない）
- **容量**: 暗号文は平文の約 1.33 倍（base64url）と項目ごとに 28 バイト。1 席の上限（100 件・本文 4000 字）いっぱいで、1 席だけでもカプセルの上限（1.9 MB）に届きうる（届けば保存は 413）
- **確かめ方**: `bun aws/verify.ts …` は、AWS dev のスタックのときだけテーブルを `scan` して、書いた個人メモの目印が保存された payload のどこにも無いことを見る（同じ読み方でその旅行の題が見つかることも見て、読み方が正しいことを確かめる）。prod では実カプセルがあるのでテーブル全体は読まない

### 1.5 生成と検査

LLM の出力は、そのまま公開しない。LLM に渡す手順は [旅程の Recipe](recipes/trip.md)、発行せずに 1〜2 を行うコマンドは `bun run validate <file>`。

画面からの経路: しおりの画面が `GET /v1/recipe` で Recipe を配り、利用者が自分のチャットに貼る。返ってきた答えは `POST /v1/check` に貼り戻し、Host が旅程を取り出して（前後の文・コードフェンス・途中で切れた答えを見分ける）同じ検査にかけ、結果を日本語で返す。どちらの経路もカプセルには触らない。

**Host での生成**: 生成は Host が、作成者が登録した自分の Anthropic API キーで行う（`POST /v1/assist`。鍵の保管は §5.8。作成者ごとに 1 分 2 回・同時 1 件、Host 全体で同時 2 件）。生成の費用は鍵の持ち主に行き、Host の運用者は払わない。貼り付けの道もある。下の検査の手順は、誰が生成しても変わらない。

1. JSON Schema で検証する。
2. 日付、タイムゾーン、モジュール参照、上限値を意味検査する。
3. Markdown を sanitise し、URL の scheme を `https:` に限定する。
4. ローカル preview で owner が確認する。
5. 検査済み Spec のハッシュとともに公開する。

公開後に LLM で作り直す場合も、新旧の差分を見せて owner（または editor）が承認する。既存 Document を読めなくする破壊的な変更は拒否する:

- **owner と editor** が、今の旅程と直し方（[旅程の Recipe](recipes/trip.md) の「直すとき」）をコピーできる（`GET /v1/c/:id/revise`）。入口は owner が「共有・管理」→「チャットで直す」、editor がヘッダーの「チャットで直す」。editor に渡すのは ZIP で書き出せる範囲の内で、持ち出せるものは増えない。画面の「直してほしいこと」に書いた頼みは、画面がコピーする文の最初に `## 直してほしいこと` として付ける（貼った先で文が切れても頼みが残るように）。コピーする文には Recipe の「例」を入れず、旅程の JSON は字下げしない（長い文は貼った先で切れるため）。Host には送らない（旅程の中身を含み得る文を URL やログに載せない）。渡すのは Spec と Document の `items`・`checklist`・`notes`・`budget`・候補（`id`・`body`・`promoted`）・相談（`id`・`body`）。候補・相談の書いた人の名前と投稿時刻、思い出、版数、メンバーと招待の情報は渡さない
- 直した答えを貼ると、Host が新規作成と同じ検査（`extract` → `check()`）を通し、**今の旅程との差分**を出す（`POST …/revise/check`。書き込まない）: 題・日程・削除期限・足したページ、予定・候補・相談ごとの追加 / 変更（項目の前→後）/ 削除、それ以外に変わる所の名前。差分は画面ではなく Host が計算する
- 反映（`POST …/revise`）は、差分を出したときの版を If-Match に添える。同じ答えと同じ版からは同じ差分が出るので、見せた差分を保存せずに「見せた差分そのもの」を反映でき、その間に誰かが更新していれば 409 で差分を出し直す
- **大きな変更**（題か日程が変わる、今の予定の半分以上が削除・変更される、または今ある候補・相談が変更・削除される）は、完全削除と同じく旅行の題の入力が要る。小さな変更はチェック 1 つ
- 答えから候補・相談も取り込む。既存 id は更新、新しい id は追加、配列から無くなった id は削除。既存投稿の書いた人と時刻は今のもの、新しい投稿は反映した owner・editor のメンバー名と反映時刻を Host が付ける（答えの author・createdAt は使わない）。思い出とチェックの状態、メンバー・招待リンクは今のものが残る。ページを消す・削除期限を過去にする答えは拒否し、共有終了後は反映できない
- 候補から追加した予定が、反映・戻すで旅程から消えたら、その候補は再び旅程へ追加できる（候補が作った予定の id を `itemId` に残し、予定が無くなった候補の `promoted` を戻す。`itemId` の無い古い候補は追加済みのまま）
- **editor の反映では Spec（題・日程・削除期限・ページ・見た目・参加者にできること）は変わらない**（§2.2 で Spec の変更は owner だけ）。Host は答えの `spec` を今の Spec に置き換えてから検査するので、答えに `spec` が無くても、題や期限を変えていても、差分に出るのは予定・候補・相談・準備リスト・メモ・費用メモだけ。editor にコピーする文には「`spec` は変えずに返す」と書き添える
- 反映の直前の設定・予定・候補・相談・準備リスト・メモ・費用メモを 1 世代だけカプセルに残し（`previous`）、owner は差分を見て **1 つ前に戻せる**（`GET/POST …/undo`）。反映で変えた候補・相談も戻り、反映の後に書かれた候補・相談、思い出とチェックの状態は残る。反映後に手で直した候補・相談も元に戻り、手で消した投稿は復元される（戻す差分に出る）。候補・相談を持たない古い previous は、今の投稿に触れずに戻す。戻せるのは 1 回で、次の反映で残す 1 世代は置き換わる。戻すときだけ、反映で足したページが消えることを許す（そのページの投稿は Document に残る）。戻すときも、大きな変更なら旅行の題の入力が要り、削除期限が過去に戻る場合は拒否する。editor が戻せるのは、戻しても Spec が変わらないときだけ（owner が題や期限を変えた反映の後は、`403`「設定も戻るため、オーナーだけが戻せます」）。残す 1 世代は誰の反映でも置き換わるので、owner が題を変えた反映の後に editor が反映すると、owner もその題の変更には戻れない

## 2. Capability Link と権限

### 2.1 招待リンクは席の引換券、権限は登録したブラウザの Cookie が持つ

リンクは何度でも使える合鍵ではなく、決まった人数分の席を配る引換券として扱う。パスワードも名前入力もなしで、リンク漏洩の被害を「受付期間中の空席」に限定することが目的である。

```text
https://trip.example/c/<public-id>?openExternalBrowser=1#k=<secret>
```

`public-id` はカプセルを探すための不透明な ID、`secret` は 128 bit 以上の暗号学的乱数とする。秘密を query や path に入れないため、HTTP リクエスト、通常のアクセスログ、Referer、リンクプレビューのクローラーには載らない。`openExternalBrowser=1` は LINE に既定ブラウザで開かせ、アプリ内 WebView に席を取らせないための指定で、サーバーは解釈しない。

1. owner は role・席数・受付期限（既定3日）を決めて招待を発行し、1本のリンクをグループへ送る。
2. 開いた人には参加画面を出し、「この端末で参加する」を押した時点で `POST /v1/c/<id>/sessions` が secret を引き換える。自動では引き換えない（アプリ内ブラウザや意図しない端末が席を消費するのを防ぐ）。
3. サーバーは席を1つ消費し、そのブラウザ専用の乱数を `HttpOnly; Secure; SameSite=Strict` cookie で返す。以後の権限はこの cookie だけが持ち、転送できるリンクは残らない。cookie は持っている人なら誰でも使える（bearer）。端末には縛られず、コピーされた cookie は別の端末からも通る（§2.4.1）。cookie の期限は Grant 期限までとし、旅程取得のたびに更新する。ただし 30 日使わなければ失効し（最終利用 `seen` は旅程取得のときに 1 日 1 回だけ記録する）、メンバーは自分でログアウトできる。絶対期限は Grant 期限のままで、放置 30 日の失効は共用端末に置き忘れた cookie を止めるためのもの。使われ続ける盗まれた cookie は放置では止まらないので、owner によるメンバーの失効と、重要操作の前のパスキーでの本人確認（§2.2）で抑える。
4. 定員に達するか受付期限を過ぎた招待は誰にも使えない。登録済みブラウザが同じリンクを開き直すのは席を消費しない。
5. 引換は `ClaimCountries`（既定 JP）の国からだけ許可する。登録後のアクセスには国制限をかけない（旅行先が国外であり得る）。
6. 招待は承認方式を選べる（`approval`。既定は `auto`）。`owner` の招待は席を引換時点で消費するが、引き換えた人は承認されるまで `pending` で、旅程を取得できず（`GET` は 403）、本人の画面に 6 桁の確認コードだけが出る。コードは照合用で秘密ではなく、本人の Cookie を持つブラウザと owner（`GET grants` の members）にだけ見える。引き換えた人がそれを LINE など別の経路で owner に伝え、owner が一覧のコードと照らして承認（`POST approve`）か拒否する。拒否はメンバーを消すが席は戻らない（§2.3 のメンバー失効と同じ）。owner 招待は常に自動。通知は作らない（owner が「共有・管理」を開いて見る）。

**パスキー（任意）**：登録済みのメンバーは、自分の席にパスキーを 1 つ足せる（WebAuthn。Face ID・指紋・PIN）。足しておくと、cookie を失っても「パスキーで戻る」で同じメンバーに戻れ、PC のブラウザからも OS 標準の QR 連携でスマホのパスキーを使って同じメンバーとして入れる（§2.3）。必須にはしない。画面ロックを設定していない同行者も、今までどおり cookie だけで参加できる。**初回の登録は Cookie を持つブラウザならできる**（サーバーからは本人と盗まれた Cookie を区別できないので、登録した時点を信頼の起点にする）。**登録済みのパスキーの置き換え**（「パスキーを登録し直す」）は、同じリクエストに今のパスキーでの確認（別の未使用の challenge への assertion）が要る。重要操作のための 5 分の本人確認（`verifiedUntil`）は使えず、置き換えで変わりもしない（別の操作のための確認を転用させない）。Cookie だけでは別のパスキーに差し替えられないので、盗まれた Cookie が席の長期の乗っ取りにならない。サーバーが保存するのは credential ID・公開鍵・鍵の種類・署名カウンタだけで、秘密鍵は端末から出ない。ceremony の検証（origin、RP ID、ユーザー検証、署名、署名カウンタの前進）は `src/webauthn.ts` が依存なしで行い、challenge の発行と使い捨ては `src/cloud-host.ts` が担う（§2.3）。RP ID は `PublicOrigin` のホスト名。パスキーも cookie も Origin に紐づくので、旅行の途中で Distribution を作り直さない（ドメインが変わると進行中の旅行の登録が無効になる）。独自ドメインは前提ではない。

Web からハードウェア識別子は取得できず、指紋は偽装でき本人も締め出すため使わない。権限を持つのは「登録したブラウザに保存された cookie」で、端末ではない。cookie は持っている人なら誰でも使えるので、通常は登録したブラウザから使われるというだけで、別の端末からの利用を拒む仕組みは無い。User-Agent は owner のメンバー一覧に表示する目印に限り、認可には使わない。メンバー名は「メンバーN」と自動採番し、owner が後から付け替えられる。

DB には secret を保存せず、サーバー秘密鍵を使った HMAC-SHA-256 の結果だけを保存し、比較は constant-time で行う。アクセスログ、エラーログ、解析、サポート情報にも secret を残さない。すべての変更 API は同一 Origin を要求する。

### 2.2 ロール

| 操作 | owner | editor | participant | viewer |
|---|---:|---:|---:|---:|
| 旅程を見る | ✓ | ✓ | ✓ | ✓ |
| 確定旅程を編集する（予定の追加・変更・同じ日の中の並べ替え） | ✓ | ✓ | — | — |
| 候補・コメントを追加する | ✓ | ✓ | Spec 次第 | — |
| 候補・相談の投稿の本文を直す・投稿を消す | ✓ | ✓ | — | — |
| 準備リストのチェックを付ける・外す | ✓ | ✓ | Spec 次第 | — |
| 準備リスト・費用メモの項目を追加・変更・削除する | ✓ | ✓ | — | — |
| チャットで旅程を直す・1 つ前に戻す（editor は Spec を変えない範囲だけ） | ✓ | ✓ | — | — |
| Spec・テーマを変更する | ✓ | — | — | — |
| 招待を出す（出せる役割。下の「出せる招待」） | 全部 | viewer だけ | — | — |
| 招待・メンバーを交換・失効する | 全部 | 自分が出した招待とそのメンバーだけ | — | — |
| 期限変更・終了・完全削除 | ✓ | — | — | — |
| 足あとを残す（旅行期間中だけ） | ✓ | ✓ | ✓ | — |
| 写真を上げる（共有終了まで） | ✓ | ✓ | ✓ | — |
| 写真を消す | ✓（どれでも） | ✓（どれでも） | 自分が上げたものだけ | — |
| 写真を載せる予定・一言を直す（共有終了まで） | ✓（どれでも） | ✓（どれでも） | 自分が上げたものだけ | — |
| 写真を見る | ✓ | ✓ | ✓ | ✓ |
| 足あとを見る | ✓ | ✓ | ✓ | ✓ |
| 足あとを消す（participant は自分の点だけ） | ✓ | ✓ | 自分の点 | — |
| 旅程のページの保存（1 ファイル） | ✓ | ✓ | ✓ | ✓ |
| Markdown のコピー | ✓ | ✓ | ✓ | ✓ |
| ZIP | ✓ | ✓ | — | — |

Markdown のコピーは、画面で読める `document`（`GET /v1/c/:id` がどの役割にも返すもの）と同じ範囲なので全員に開く。ZIP にはデータの控え（`trip.json`）なども入るので owner / editor だけ。旅程のページ（ZIP の `index.html` と同じ 1 ファイル）も、Markdown のコピーと同じく `document` の範囲なので全員に開く。

自分だけの予定・日記（§1.3）は役割表の外にある。どの役割も自分の分だけを読み書きでき、owner にも editor にも見えない。ZIP と「チャットで直す」のコピー文、Markdown のコピーにも入らない（どれも `document` から作る）。Host の運用者にも題・本文・場所は読めない（§1.4 の「運用者にも読めないもの」）。自分の分は日記カードの別の「チャットで直す」でどの役割もチャットに渡して直せるが、そのコピーは本人が自分でチャットのサービスに貼るもので、そのサービスには読める（運用者に読めないのは Host の中だけ）。

**出せる招待**（自分より強い役割は配れない）。表は `src/cloud-host.ts` の `canIssue` 1 つで、画面（「共有・管理」の権限の選択肢）はそれを写すだけ。正は Host の 403。

| 招待を出す人 ＼ 出せる招待 | owner | editor | participant | viewer |
|---|---|---|---|---|
| owner | ✓ | ✓ | ✓ | ✓ |
| editor | — | — | — | ✓ |
| participant | — | — | — | — |
| viewer | — | — | — | — |

editor の「共有・管理」は自分が出した閲覧者の招待の一覧・発行・交換・失効だけで、履歴・メンバーの名前変更・設定・終了・削除は owner のまま。editor の招待の発行・交換・失効も owner と同じくパスキーの本人確認が要る（下の表）。editor の招待も旅行全体の上限（有効なリンク 50 件・合計 100 席）に数える（editor ごとの上限は無い）。

owner 招待は常に1席で、発行時に決めた本人のブラウザが引き換える。通常の共同編集には editor、旅行メンバーには participant、家族などへの参照共有には viewer の招待を発行する。1人ずつ別の招待を作る必要はなく、1本の招待の席数で人数を決め、失効は登録されたメンバー単位で行う。

**本人確認（パスキー）が要る操作**。盗まれた Cookie だけで席を配ったり旅行を終わらせたりできないように、owner の重要操作（editor の招待の発行・交換・失効を含む）は、その端末のセッションで 5 分以内にパスキーで本人確認していなければ `428` で断る（§2.3 の `verifiedUntil`）。画面は 428 を受けるとその場で確認（パスキーが無ければ登録）して同じ操作を送り直す。

| 画面の操作 | API | 本人確認 |
|---|---|---|
| 招待リンクを発行・交換（owner リンクの交換を含む） | `POST grants`（`rotate` つきを含む） | 要る |
| 招待リンク・メンバーを失効 | `POST revoke`（`id` / `member`） | 要る |
| 共有を終了 | `POST freeze` | 要る |
| 完全に削除 | `POST purge` | 要る |
| 設定・期限の変更 | `PATCH spec` | 要る |
| チャットで直す・1 つ前に戻す | `POST revise` / `POST undo` | 削除期限（`purgeAt`）が変わるときだけ要る |
| 旅程を見る・予定の編集と並べ替え・候補・チェック・思い出・メンバーの名前変更・ZIP・招待一覧・チャットに渡す旅程と差分の表示 | `GET` 全般、`PATCH document`、`PATCH members`、`POST revise/check` | 要らない。旅行中に何度も使う操作で、席や期限を動かさない |

パスキーを登録していない owner は、最初の重要操作でその場の登録を求められ、登録したことが本人確認になる（初回登録は Cookie で行える。登録した時点を信頼の起点にする）。登録済みのパスキーの置き換えにも本人確認が要るので、Cookie だけでパスキーを差し替えて確認を通ることはできない（§2.1）。

### 2.3 Grant（招待）と Session（メンバー）

```ts
type Grant = {                  // 招待
  id: string;
  role: "owner" | "editor" | "participant" | "viewer";
  digest: string;               // secret の HMAC
  label: string;                // 「旅行メンバー用」など。秘密は含めない
  seats: number;                // 引き換えられる人数
  claimed: number;              // 引換済みの数。メンバーを失効しても減らない
  claimBy: number;              // 受付期限。既定は発行から3日、expires を超えない
  expires: number;              // 登録済みメンバーがアクセスできる期限
  revoked: number | null;
  issuedBy?: string;            // 出したメンバーの Session id。公開時・recover・作成者からの owner 席の受け渡しで出た招待には無い
  approval?: "auto" | "owner";   // 引換後に owner の承認が要るか。無い既存の招待は auto
};
type Session = {                // メンバー = 登録された1ブラウザ
  id: string; grantId: string;
  digest: string;               // cookie 乱数の HMAC
  label: string; device: string;
  created: number; expires: number;
  passkey?: { id: string; publicKey: string; algorithm: -7 | -257; counter: number; created: number };  // 任意。credential ID と公開鍵だけ
  verifiedUntil?: number;       // このセッションでパスキーの本人確認をした時刻 + 5 分。無ければ未確認
  pending?: boolean;            // owner の承認待ち（承認方式 owner の招待で引き換えた直後）。待ちの間は旅程を取得できない
  code?: string;                // 承認待ちの確認コード（6 桁）。承認で消える
  seen?: number;                // 最終利用（参加・パスキーで戻る・1 日 1 回の旅程取得）。30 日過ぎた cookie は 401。無い既存の Session は今とみなし、次の取得で入る
};
```

- 招待は出した人（`issuedBy`）を覚える。交換・失効（その招待で入ったメンバーの失効を含む）ができるのは、出した本人と owner だけ（それ以外は 403）。`GET grants` は owner には全部、editor には自分が出した分だけを返し、各招待に `issuedBy: { id, label } | null` を付ける。
- 出した人が失効されても、その人が出した招待は残す（巻き込んで失効させない）。一覧では「（失効したメンバー）」が出したと出て、owner が見て失効できる。owner が自分の owner 招待を交換して席を渡したときも、前の席が消えるので、それまでの招待は同じく「（失効したメンバー）」と出る。
- メンバーの失効は席を戻さない。戻すと漏洩したリンクが再び使えるため、再参加には新しい招待を発行する。
- 招待の失効は、未使用の席とそこから登録した全メンバーを同時に無効化する。
- 旅行期間いっぱいの Grant は `purgeAt` の延長に追随する。延長で登録済みブラウザを締め出さない。
- cookie を失った参加者は、パスキーを登録していれば自分で同じメンバーに戻る（`POST passkey/session`）。challenge は保存せず署名して渡し（有効期限・乱数・カプセル ID の HMAC、5 分）、ceremony が成立したものだけを使用済みとして記録する（再利用を防ぐ。期限が切れるまでは決して捨てず、1 つの窓で 100 件に達したカプセルは忘れる代わりに新しい ceremony を断る）。戻ったブラウザには cookie の乱数を差し替えて渡すので、席は増えず（`claimed` はそのまま）、権限も同じで、古い cookie は無効になる（1 メンバー = 1 ブラウザのまま）。席の引換ではないので地域制限はかけない。パスキーは Session の項目なので、メンバーや招待を失効すれば一緒に使えなくなる。
- パスキーを登録していない参加者は今までどおり、owner がそのメンバーを失効し1席の招待を再発行して回復する。
- ログアウト（`POST signout`、画面のフッターの「この端末からログアウト」）は、そのセッションの cookie の乱数を誰も知らない値に差し替えて、ブラウザの cookie を消す。コピーした cookie を再送しても 401。席とパスキーは残るので、パスキーがあれば「パスキーで戻る」で戻れ、無ければ再招待が要る（owner なら `aws/recover.ts`）。30 日使わずに失効したときも同じで、Session は消さない。招待リンクを開き直しても、失効した cookie は「同じブラウザ」とみなさない。席そのものが無くなった（メンバーの失効、招待の交換・失効・期限切れ、共有終了、owner の回復）cookie の 401 だけは、本文に `seat: "gone"` を足す（`error` と status は同じ）。画面はそれを見て、そのブラウザに置いたその旅行の鍵と一覧の行を消す。そのため Host は、席を消すたびにその cookie の HMAC をカプセルの `left`（新しい順に最後、1000 件まで。同時に持てる席は 100 だが、編集者が閲覧の招待の発行と失効を繰り返すと増え続け、旅行が保存の上限に当たるため）に残し、`left` にある cookie だけに付ける。30 日使わずに失効した cookie と、パスキーで戻る・ログアウトで差し替わった cookie には付けない（席が残り、パスキーで戻れば同じ鍵で読めるため）。`left` に無い cookie（この記録を始める前に消えた席、1000 件から押し出された席）も付けない（鍵を消すのは取り消せないので、分からないときは残す）。`left` は応答に出さない。「全端末からログアウト」は作らない（1 メンバー = 1 ブラウザなので、自分の 1 つで足りる。盗まれた席を止めるのは owner の失効）。
- owner の重要操作（§2.2 の表）の前の本人確認は `POST passkey/verify`。入力は `passkey/session` と同じ assertion で、そのセッションのメンバー自身のパスキーで、このカプセルの未使用の challenge に署名したときだけ `verifiedUntil` を今から 5 分後にする。結果は Session の項目なので、別のメンバー（2 人目の owner を含む）・別のカプセルでは使えず、Cookie を差し替えて戻った同じメンバーには引き継がれる。拒否は理由を問わず 401 で、何も書かない。未登録のメンバーが最初のパスキーを登録したときも `verifiedUntil` を入れる。ログインと同じ IP ごとのレート制限を受ける。
- 本人確認の結果は保存しない token や Cookie にはせず、Session の 1 項目だけにする（別の表・トークンを作らない）。パスキーを持てない・失った owner の重要操作は、`aws/recover.ts` で owner 招待を別の端末へ移してから、その端末で登録して行う。
- パスキーの置き換え（`POST passkey` を登録済みのセッションで）は、同じリクエストの `check`（今のパスキーの assertion）が通ったときだけ受け付ける。拒否は 401 で、何も書かない。置き換えたのは本人確認したそのセッション自身なので、ほかのセッションを別に失効させる処理は無く、古いパスキーは置き換えで使えなくなる。

- owner が登録ブラウザを失った場合は、IAM で認可された Publisher（`aws/recover.ts`）が owner 招待を差し替える。Publisher は旅程のセッションを得ない（差し替えた owner 席も、旅行の鍵を受け取るまで暗号化した旅程を読めない）。作成者（§2.6）にはこの差し替えを開かない（カプセル ID を知っているだけで owner 席を取れてしまうため）。
- 同時引換は保存時の楽観ロック（version の一致を条件にした書き込み。ローカルの SQLite でも AWS の DynamoDB でも同じ）で直列化し、席数を超えない。
- Grant の期限はカプセルの `purgeAt` を超えられない。
- owner は Grant 一覧、最終利用時刻、role を確認できるが、発行済み secret の再表示はできない。
- 招待と owner の出入りの履歴: カプセルの `audit`（最新 2,000 件）の行に、任意の項目 `role`（対象の役割）・`label`（リンク名、メンバー失効ではメンバー名）・`by`（操作した人のメンバー名。`recover` は「発行者」、作成者の owner 招待の作り直しは「作成者」、発行の再実行はどちらか）・`device`（操作した人の端末）を残す。`GET history` は owner だけに、`publish` / `replay` / `creator-owner` / `recover` / `sessions`（新しい席の引換）/ `grants` / `rotate` / `revoke` / `revoke-member` / `freeze` の行を新しい順に返し、画面は「共有・管理」の「招待とオーナーの履歴」に出す。secret・digest・Cookie・パスキーは残さない。項目を持たない今までの行は移行せず、操作と日時だけを返す。
- **履歴が防げないこと**: owner が 2 人いるとき、片方は相手の owner 席を「交換」で失効させて締め出せ、完全削除もできる。締め出された側は履歴を開けない（これを防ぐ仕組みは無い）。履歴は、知らないうちに招待や owner が増えたことに残った owner が気づき、失効や `aws/recover.ts` での差し替えを頼むためのもの。
- ローテーションは新しい Grant を発行して古いものを即時 revoke する。
- 失効済み Grant と Session はすべての API で拒否する。
- role とカプセル ID はクライアントの申告を信用せず、Session からサーバー側で解決する。

回復の手順（新しい回復経路は作らず、既存の経路だけを使う）:

| だれが | パスキーあり（手元にある） | パスキーなし | パスキーを失った |
|---|---|---|---|
| メンバー | Cookie を失っても「パスキーで戻る」。端末を替えるときは今のパスキーで確認してから「パスキーを登録し直す」 | owner にそのメンバーの失効と 1 席の再招待を頼む | owner にそのメンバーの失効と 1 席の再招待を頼む（古いパスキーは失効で一緒に使えなくなる） |
| owner | 同上。重要操作の前の本人確認もこのパスキーで | 最初の重要操作でその場で登録する（登録が本人確認になる）。Cookie も失ったら右の列と同じ | 旅行を発行した人に `aws/recover.ts` で owner 招待を差し替えてもらい、新しい端末で開いてパスキーを登録する |

### 2.4 防御線

共通ランタイムで任意コードを動かさないことが最大の防御線になる。加えて以下を必須とする。

- strict CSP（`connect-src` は `'self'` と、暗号化した旅行の「ここで直す」でブラウザが Anthropic に直接送るための `https://api.anthropic.com` だけ）、Markdown sanitise、出力時の context-aware escaping
- 外部リンクに `noopener noreferrer`
- IP ごと（ログイン系は別に厳しく）と、認証済みの要求だけのカプセル・Grant ごとのレート制限
- body size、フィールド長、配列件数、総容量の上限
- CSRF 用の Origin 検査
- owner の重要操作はパスキーで本人確認（§2.2）、書き込む操作には監査イベント
- 第三者広告・解析スクリプトを置かない

- API は CloudFront の OAC の署名がある要求だけを受け、Web Function への直接アクセス（国ヘッダーの偽装経路）を拒否する

残るリスクは、受付期間中にリンクが漏れて他人が先に空席を取ることである。席数・受付期限・国制限・owner のメンバー一覧と個別失効、機密度の高い旅行では owner 承認の招待（§2.1 の 6。確認コードを別の経路で照合するまで旅程は開かない）で抑えるが、パスワードなしの代償として受容する。機密性が必要な旅行は対象外と明示する。予約番号・本名・住所・連絡先など、旅程に書いたものは、有効な cookie を持つ人（盗んだ人を含む）全員に見える。閲覧の漏れも許せない情報はカプセルに置かず、置くかどうかは下の表の残るリスクを見て判断する。

#### 2.4.1 誰がアクセスできるか（脅威と残るリスク）

旅行を開けるのは「有効な cookie を持つ人」である。パスキーは cookie を失ったときの戻り道と、owner の重要操作の前の本人確認で、閲覧は守らない。各行の根拠は `src/cloud-host.ts` の該当箇所。

| 脅威 | 基本の対策 | 追加の対策 | 残るリスク |
|---|---|---|---|
| **cookie の盗難**（マルウェア・共用端末・端末のバックアップ・画面を開いたまま渡す） | cookie は `HttpOnly; SameSite=Strict`、HTTPS では `Secure`、`Path=/v1/c/<id>`（`setCookie`）。DB には cookie の HMAC だけ（`session` が `digest` で引く）。変更 API は同一 Origin を要求。owner はメンバー単位・招待単位で失効できる（`route` の `revoke`）。パスキーを登録済みの席は、本人が別のブラウザから「パスキーで戻る」と cookie の値が差し替わり、コピーは 401（`route` の `passkey/session`） | owner の重要操作は 5 分以内のパスキーでの本人確認が要る（`verified`、`passkey/verify`。§2.2 の表）。登録済みのパスキーの置き換えは同じリクエストで今のパスキーの確認が要る（`route` の `passkey`）。本人のログアウトで cookie の値を差し替え、コピーは 401（`route` の `signout`）。30 日使われない cookie は 401（`idle`）。**作成者の Cookie**（`Path=/v1`、12 時間）では、API キーの登録・置き換え・削除とオーナーのいない旅行の受け取り直し・削除に、サインインから 5 分以内が要る（`recentCreator`。§2.6） | 有効な cookie を持つ間は、その役割の閲覧・編集が誰にでもできる（本人確認は閲覧・予定の編集・候補・チェックには求めない）。**パスキー未登録の席**では、盗んだ人が最初のパスキーを登録でき（初回登録は cookie で可）、以後その席の戻り道と、owner なら重要操作も握る。使われ続ける cookie は放置の失効では止まらず、止めるのは本人のログアウト・「パスキーで戻る」（パスキー登録済みの席）か、owner の失効（owner 自身の席なら `aws/recover.ts`）。**作成者の Cookie** では、12 時間のあいだ生成（作成者の鍵の費用を使う。1 分 2 回・同時 1 件）と旅行の保存（1 分 5 回、保持 10 件）ができる |
| **招待リンクの漏洩**（グループの外への転送、スクリーンショット） | secret は URL の `#` の後ろで、サーバーのログ・Referer に載らない。DB には HMAC だけ。席数・受付期限（既定 3 日）で使える回数と期間を区切り、定員か期限の後は誰にも使えない（`route` の `sessions`）。引換は `ClaimCountries` の国からだけ（同）。owner は招待の失効・交換ができる | 招待の発行・交換・失効に owner の本人確認（`verified`）。owner の席にパスキーが登録済みなら、盗んだ cookie だけでは新しい招待を出せない（未登録なら、盗んだ人が最初のパスキーを登録して確認を通れる。上の行） | 受付期間中の空席は、リンクを持つ先着の誰でも取れる。取った人は正規のメンバーと区別できず、owner がメンバー一覧（端末の目印・登録日）で見つけて失効するまで使える |
| **端末の紛失** | 画面ロックは OS の保護に任せる。owner はそのメンバーを失効できる。owner の端末なら `aws/recover.ts` で owner 招待を差し替え、古い owner の cookie を無効にする（`route` の `recover`：古い owner 招待を失効し、`session` が失効した招待の cookie を拒む） | 30 日使われなければ失効（`idle`）。owner の席にパスキーが登録済みなら、拾った人は重要操作にそのパスキーの確認（Face ID・指紋・PIN）を通す必要がある（`verified`）。未登録なら、拾った人が自分の認証器で最初のパスキーを登録でき、それが確認になる | 画面ロックの無い・解かれた端末では、失効まで旅程を読める。本人のログアウトはその端末のブラウザでしかできないので、止めるのは「パスキーで戻る」（パスキー登録済みの席なら、別のブラウザから。拾われた端末の cookie は 401 になる）か、owner の失効か `aws/recover.ts` |
| **運用者（IAM）の回復権限** | IAM で認可された人だけが `aws/recover.ts`（owner 招待の差し替え）と `aws/capsules.ts`（一覧・強制終了。`route` の `terminate`）を実行できる。これらは旅程のセッションを得ない。作成者には `/recover` を開かない | 旅程・足あと・名前を旅行の鍵で暗号化する（§1.4） | IAM で `aws/recover.ts` を実行できる人は、どの旅行の owner 席も出し直せるが、出し直した席は旅行の鍵を持たず、ほかのメンバーから確認コードで受け取るまで旅程を読めない。データストアを読める IAM の権限でも、読めるのは暗号文と平文の部分（日付・時刻・件数・全体の大きさ・役割・だれの記録か、Host が付けた名前）だけ（§1.4）。例外は、発行から owner が席を取って暗号化するまでの旅行と、owner がまだ新しい画面で移していない旅行で、平文の間は読める（§1.4）。また画面の JavaScript を配るのは運用者なので、復号した旅程を送り返すコードを配れば読める（§5.3 の閉じない経路）。平文の間とこの閉じない経路を除けば、運用者は旅程の中身については信頼境界の外にあり、握るのは可用性（止める・消す・席を出し直す）だけ |

パスキー自体は OS のアカウント（iCloud キーチェーン・Google パスワード マネージャー）で同期されることがあり、その OS のアカウントを使える人は「パスキーで戻る」で同じ席に戻れる。

重要操作だけ本人確認でも、有効な cookie が盗まれている間の旅程の閲覧は防げない。閲覧の漏れも許せない情報はカプセルに置かない。

### 2.6 作成者（新しい旅行を作る人）と旅行の owner

新しい旅行を作る権利は、旅行の中の役割（owner）とは別に持つ。作る権利は IAM（Publisher）と、**パスキーでサインインした作成者**が持つ。作成者は**作れるが読めない**（作成者は旅行の鍵を持たない。暗号化した後の旅程は、運用者も作成者も暗号文しか読めない。暗号化する前の平文の間は §1.4）。

| | 作成者 | 旅行の owner |
|---|---|---|
| 単位 | Host 全体に 1 人ずつ | カプセルごとの席（§2.3） |
| なる方法 | 運用者の CLI（`bun aws/creator.ts enroll`、IAM）が出す 1 回限り・1 日の登録リンクを開き、パスキーを作る。または、作成者が旅行の owner に分けた委任リンク（1 回限り・1 日）を、その旅行の owner 席のある端末で開き、パスキーを作る（分けられた作成者。さらには分けられない） | owner 招待を引き換える。作成者が保存した旅行は、保存したときに作成者が選ぶ: 「この端末をオーナーにする」（その場で引き換える）か「オーナーリンクを受け取る」（別の端末・別の人に渡す。受付 3 日）。既定は無い。引換の地域制限（§2.1）は同じで、通らなければ画面から再試行・リンクの受け取り。選ばずに閉じた旅行は、作成者のトップの「オーナーを決めていない旅行」からあとで決められる |
| パスキー | **必須**。複数持てる（「別の端末を追加」で、サインイン中の端末の作成者のパスキーで確認してから 1 回限りのリンクを作り、別の端末で開く） | 任意（§2.1） |
| できること | 新しい旅行の保存（`POST /v1/publish`）、作り方（`GET /v1/recipe`）と貼り付けの確認（`POST /v1/check`）。自分が作り、まだオーナーが一度も決まっていない旅行の一覧（題名・日程・削除予定）・オーナーリンクの受け取り直し・削除（`POST /v1/creators/trips`） | その旅行の閲覧・編集・招待・終了・削除（§2.2） |
| できないこと | **どのカプセルも読めない**（自分が作った旅行も。一覧に出るのは題名・日程・削除予定だけ）。オーナーが決まった旅行に関わること。owner 招待の差し替え（`/recover`） | 新しい旅行を作ること（作成者でなければ） |
| 失効 | CLI（`bun aws/creator.ts revoke`）で作成者ごと、またはパスキー 1 本ごと。分けられた作成者は、分けた作成者もトップの「分けた作成者」から失効できる（`POST /v1/creators/revoke` を作成者の cookie で。分けた相手のほかは 404）。パスキーを 1 本失効すると、その作成者の未使用の端末追加リンクと委任リンクも消える。作成者を失効すると、その人の未使用の委任リンクも消えるが、分けられた作成者は残る。作った旅行と owner 席は残る | §2.3 |

- 作成者の登録簿は、既存の表の 1 行（カプセルと同じ version CAS）。登録リンクは secret の HMAC だけを持ち、使ったら消す。パスキーは credential ID・公開鍵・署名カウンタだけ（§2.1 と同じ）。分けられた作成者は `delegatedBy`（分けた作成者の ID）を持ち、委任リンクは `ownerOf`（引き換えられる旅行の ID）と `by`（出した作成者の ID）を持つ。
- 作成権限の委任: 作成者が `POST /v1/creators/enroll` に `ownerOf` を添え、端末の追加と同じく同じリクエストに自分のパスキーの assertion を付けると、委任リンク `/c/<id>#delegate=<secret>` が出る（作成者ごとに未使用 3 件。IAM の 20 件とは別に数える）。引換は `POST /v1/c/<id>/creators/register` だけで、その旅行の cookie が届く道の下で owner 席を確かめる（cookie 無しは 401、owner でない席は 403、別の旅行の ID・`/v1/creators/register` への委任リンクは 401）。owner 席の本人確認（`verified`）は求めない（作成者のパスキーを同じリクエストで作り、委任リンクの secret も要るため）。旅行は書かず、作成者の cookie で旅行を開く道は増えない。
- 作成者のセッションは保存しない。作成者 ID・パスキー ID・期限を HMAC で署名した `HttpOnly; Secure; SameSite=Strict; Path=/v1` の cookie（12 時間）で、使うたびに登録簿で作成者とパスキーの失効を確かめる。
- 作成者のサインアウト（`POST /v1/creators/signout`、トップの作成者のカードの「サインアウト」）は、その cookie のパスキーに `signedOut`（時刻）を記録し、それまでにそのパスキーで出した cookie をすべて拒否する。同じ作成者の別の端末のパスキーはサインインしたまま。セッション表は作らない（登録簿のパスキーごとの 1 項目）。もう一度パスキーでサインインすれば入れる。
- 作成者の API キーの登録・置き換え・削除（`PUT` / `DELETE /v1/account/key`）と、オーナーのいない旅行のオーナーリンクの受け取り直し・削除（`POST /v1/creators/trips` の `owner` / `purge`）は、その Cookie を出したサインインから 5 分以内でないと `428`（盗まれた Cookie だけで鍵を差し替え・消したり、旅行を受け渡し・消したりさせない）。サインインの時刻は Cookie に署名した期限から出し（期限 − 12 時間）、5 分は旅行の owner の本人確認と同じ。再確認はふつうのサインインのし直しで、新しいエンドポイント・Cookie・登録簿の項目は無い。画面は 428 を受けるとその場でサインインし直して同じ操作を 1 回送り直す。そのとき OS に出すのは、この端末が最後にサインインしたパスキーだけ（端末に覚えた credential ID。1 台に 2 人の作成者のパスキーがあっても、別の作成者で送り直さない）。覚えていなければサインインだけして送り直さず、もう一度押してもらう。生成（`/v1/assist`）・保存（`/v1/publish`）・一覧・`GET /v1/account` は Cookie のまま。IAM の発行者の身元とローカルプレビューは Cookie を使わないので対象外
- 端末の追加（`POST /v1/creators/enroll` を作成者の cookie で）は、cookie だけでは受け付けない。同じリクエストに、その作成者自身の失効していないパスキーの assertion（未使用の challenge）が要る。確認の結果は保存しない（cookie と同じく登録簿に状態を持たない）。拒否は 401 で、何も書かない。
- 公開の HTTP 経路からの publish は、**パスキーでサインインした作成者のものだけ**を受け付ける（それ以外は 401）。IAM の Publisher（`aws/publish.ts`）は今までどおり。保持上限（10 件）と作成レート（1 分に 5 件）は作成者ごとにかかる。
- 作り方・貼り付け・ファイル取り込みはトップ画面で作成者としてサインインしたときだけ出す。未サインインのトップに出るのは、この端末で参加中の旅行・招待リンクの案内・「作成者としてサインイン」だけ。
- パスキーを作れない環境（WebAuthn の無いアプリ内ブラウザ、画面ロックの無い端末）では作成者になれない。登録リンクはパスキーが検証に通るまで消費しない。
- 作成者の Cookie と、選んだ場合の owner の Cookie は別の資格で、同じブラウザに並ぶことがある。旅行を開けるのは owner の Cookie のおかげで、作成者の権利ではない（作成者として別の端末でサインインしても、その旅行は開けない）。
- 保存の応答を失ったとき（通信が切れた、Host が 5xx を返した）は、同じ画面で「この内容でカプセルを作成」をもう一度押す。画面は保存ごとに操作 ID（このタブの `sessionStorage`）を送り、Host はカプセル ID を操作 ID と発行者から導くので、二重には作られない。前回の保存が通っていて、owner の招待が**まだ誰にも引き換えられておらず受付期限の前**なら、Host はその招待を消して新しい owner リンクを返す（前のリンクは無効。受付期限は最初の招待と同じで、再送しても延びない）。席が埋まっているか受付期限を過ぎていればリンクは返らず、画面はトップの一覧（受付期限を過ぎただけのとき）と `aws/recover.ts`（オーナーが端末を失ったとき）を案内する。作成者が再送で得るのは、失った最初の応答が渡したはずのものだけなので、「作成者の権利ではどのカプセルも読めない」は崩れない。作成者に `/recover` は開かない（引き換え済みの席を取り直せてしまう）。IAM の発行者（`aws/publish.ts`）の再送も同じ条件でリンクを返し、`aws/publish.ts` はそれを保存する。リンクが無ければ `/recover` で出し直す（IAM はもともと `/recover` を持つので、権限は増えない）。
- オーナーを選ばずに閉じた・ページを更新した旅行も、作成者のものとして残る。作成者の登録簿の項目に、その作成者が作った旅行の ID を**旅行を作る前に**書き、作成者のトップに「オーナーを決めていない旅行」として題名・日程・削除予定を出す。そこから、owner 招待をすべて除いて新しいオーナーリンク（受付 3 日）を受け取り直すか、旅行を削除する（作成者の Cookie と確認だけ。まだ誰の旅行でもないため）。owner の席が初めて引き換えられた時点で旅行は引き渡され（カプセルの `ownedAt`）、以後は一覧から外れ、作成者は何もできない。引き渡しの後は、IAM の `/recover` で owner 招待が差し替わっても作成者には戻らない。引き渡しの前に IAM が `/recover` で出したリンクは、作成者が一覧から受け取り直すと使えなくなる（owner 招待はすべて出し直すため）。この仕組みより前に作ったオーナー不在の旅行は ID がどこにも無いので一覧に出ず、削除予定日の自動削除に任せる。
- 作成者が旅行の owner に作成権限を分ける（委任）のは上の「作成権限の委任」。分けられた作成者がさらに分けること（再委任）は無い。

## 3. 終了・エクスポート・削除

### 3.1 状態遷移

```text
draft (local only)
  └─ publish ─→ active
                   └─ trip ends ─→ reflection
                                        └─ reflection window ends ─→ frozen
                                                                         └─ purgeAt ─→ purged

owner: stop sharing ─→ frozen
owner: erase now    ─→ purged
```

| 状態 | 許可すること |
|---|---|
| `draft` | ローカル preview、Spec 修正。公開 URL はない |
| `active` | role と Spec に従って旅程、候補、コメント、チェック項目を更新 |
| `reflection` | 確定旅程は固定。owner/editor は訂正可能。参加者は感想・振り返りだけ追記。開くと最初に旅の記録（`story` のページがあれば。§1.3） |
| `frozen` | 全員読み取り専用。owner/editor はエクスポート可能。開くと最初に旅の記録（`story` のページがあれば） |
| `purged` | すべてのリンクと Session を拒否し、本文データを削除。HTTP 410 |

既定値は `reflectionDays = 7`、`purgeAt = trip.endsOn + 30日` とする。ただし `purgeAt` は作成から最大 180 日。作成画面では終了日を必須にし、「無期限」は提供しない。

状態遷移を cleanup job だけに依存させない。すべてのリクエストで現在時刻から有効状態を再計算し、期限を過ぎたアクセスは直ちに拒否する。cleanup が遅れてもデータを読めてはいけない。

### 3.2 旅行後の出力

出力の正本は、アプリを必要としない可搬な ZIP とする。ZIP の前に、同じ `README.md` の本文を `GET /v1/c/:id/export.md`（`{ text }`）でテキストとしてコピーできる（どの役割も。スマホで ZIP を扱わずにメモアプリへ残すため。Spec の `exports` には従わない）。ZIP の `index.html` と同じ旅程のページを `GET /v1/c/:id/export.html`（`{ text }`）で 1 ファイルとして保存できる（どの役割も。Spec の `exports` には従わない）。`text/html` では返さず、メンバーの書いた文を含むページをアプリの Origin で描画させない。暗号化した旅行では、Host は中身を読めないので `export`・`export.md`・`export.html` を 409 で断り、画面が開いた旅程から同じ関数（`src/export.ts`）で同じ形のファイルを作る（ZIP は owner / editor だけなのも同じ。開けない記録はファイルに入れず、件数を画面に出す）。

画面の「旅を保存」は保存のしかたを選ぶ画面を開く: 「旅程のページを保存」（全員。共有シートにファイルを渡せるブラウザでは共有シートに `text/html` のファイルを渡し、渡せなければ `trip-<初日>.html` としてダウンロードする。共有シートはタップの直後にしか開かないので、画面を開いたときに取得を始めておく）、「Markdown をコピー」（全員。クリップボードに書けないブラウザでは本文を全部選んだテキスト欄を出す）と、owner / editor には「ZIP を保存」。ZIP の側には、スマホでは「ファイル」アプリ（iPhone）やファイルマネージャ（Android）で ZIP をタップすると展開されることと、その旅行の `exports` にあるファイルごとの開き方（`README.md` はメモや Markdown のアプリ、`trip.json` はデータの控え、`calendar.ics` はカレンダーに取り込む、`index.html` はブラウザで開く）を書く。「共有・管理」と期限前の促し文も同じ画面を指す。

```text
trip-2026-taiwan/
  README.md          # 人が読む旅行記。日別旅程、決定、振り返り
  trip.json          # schemaVersion 付きの損失なしデータ
  calendar.ics       # 決定（confirmed）で時刻のある項目。仮置きの時刻（timeTentative）もその時刻で入る
  index.html         # サーバー不要の読み取り専用ビュー
  manifest.json      # 作成日時、元カプセル、各ファイルの SHA-256
```

`README.md` には YAML frontmatter を付け、Knowledge や一般的な Markdown 管理へそのまま保存できる形にする。コメントをすべて日記へ混ぜず、owner/editor が「記録へ含める」と指定した振り返りだけを本文に載せる。

自分だけの予定・日記は ZIP にも `export.md` にも入らない。本人の分は画面の「自分のメモを保存 ↓」でブラウザが作る（どの役割も自分の分だけ。`src/private-entries.ts` の `privateMarkdown`）。日付ごとの見出しの下に予定（`- **HH:MM 題** 本文`、時刻は旅行のタイムゾーン）と日記を並べた Markdown 1 本で、ファイル名は `trip-<初日>-private.md`。その端末で読めなかった項目は入れず、見出しの下に「この端末で読めなかった n 件は含まれていません。」と書く。1 件も読めなければボタンを出さない。

エクスポートは同じ revision から決定論的に生成し、生成中の変更を混ぜない。成果物には capability secret、Session ID、内部監査ログ、削除対象の個人メタデータを含めない。PDF は作らず、必要なら `index.html` を利用者側で印刷する。

### 3.3 終了と削除を分ける

owner には意味の異なる 2 操作を提供する。

- **共有を終了**: 全 participant/viewer/editor Grant を即時 revoke し `frozen` にする。owner は期限まで出力できる。
- **完全に削除**: 全 Grant と Session を revoke し、出力猶予もなく `purged` にする。カプセル名を入力する確認を経て、取り消せない。

共有終了・メンバーや招待の失効・削除では、消えた席の自分だけの予定・日記も一緒に消える（owner や他のメンバーに渡らない）。共有終了の後も owner の席は残るので、owner 自身の分は読めて「自分のメモを保存 ↓」で持ち出せるが、書き足せない。

自動期限では、まず論理削除を 1 トランザクションで行う。

1. 状態を `purged` にする。
2. Grant と Session を無効化する。
3. 削除ジョブを作る。
4. 以降のアクセスへ 410 を返す。

物理削除ジョブは冪等にし、Document、変更履歴、写真の画像本体、KV Session の順に削除して、失敗時は再試行する。写真の画像本体は行を空にする前にその旅行の置き場（行のキーの prefix）ごと消し、消せなければ行を残して次の sweep でやり直す。AWS の画像の置き場には、作成から 181 日で消える規則を最後の歯止めに付ける。運用確認用として `H(publicId), purgedAt, deletionStatus` だけの tombstone を最大 30 日保持してよいが、タイトル、行き先、参加者情報は残さない。

「削除」は一次ストアからの削除と即時アクセス不能を意味する。クラウド事業者のバックアップ保持期間まで即時消去できるとは表現せず、採用事業者の保持方針を公開時に明記する。

### 3.4 期限通知

利用者アカウントもメールアドレスも持たないため、メールなどの通知は送らない（通知先を登録する仕組みも無い）。期限は画面に出す。

- 旅行の画面の上部に、今の状態（「旅の準備・旅行中」「思い出を追記する期間」「共有終了・読み取り専用」）と自動削除の日付・あと何日かを常に出す。
- 削除の 7 日前から、owner・editor の画面のその欄に「削除前に「旅を保存」で書き出してください」を足す。

## 4. 対象外（このアプリがしないこと）

- アカウント、組織、友達一覧
- 航空券・ホテル予約 API との連携
- 外部の配信元から読み込む地図 SDK・地図 API・タイル配信サービス（足あとの地図は、同梱の MapLibre で自分たちの配信元に置いた地図データを描く。§1.3）、経路探索、位置情報の追跡（見張って残し続けること。押したときに 1 回だけ残す足あとと、オンにした端末で開いた・戻った時に 1 回だけ残す足あとは §1.3）
- 決済、割り勘、送金
- 任意コード、任意 HTML / CSS、外部プラグイン
- 写真以外のファイルのアップロード、写真の原本（元のまま）の保存・配信、動画・Live Photo
- 厳密な本人確認、監査要件を持つ用途
- WebSocket によるリアルタイム共同編集
- 無期限公開

Host が LLM を呼ぶのは旅程の生成（作成者の API キーで）だけで、任意コードは生成しない。自由度はモジュールとテーマの追加で広げ、任意コード実行は別の sandbox deployment として設計する。この線を守ることが、使い捨てアプリの運用費と安全性を両立させる条件になる。

## 5. データの扱い

旅行のデータがどこに、どの形で置かれ、だれに読めて、いつ消えるか。ここで「運用者」は Host を配置して動かす人（AWS なら、そのアカウントの IAM でテーブル・バケット・ログを読める人）を指す。

### 5.1 旅行の鍵と受け渡し

- **旅行の鍵**: 旅行ごとにランダムな鍵（AES-GCM 256）を 1 本作り、旅程・足あと・名前・写真をそれで暗号化して置く（§5.2）。鍵を作るのは owner の席を初めて取ったブラウザで、作成者・CLI の発行者は鍵を持たない（§2.6、§5.4）。鍵を替えると世代の番号が 1 つ増える（§5.5）
- **席の鍵の組**: 席ごとに X25519（包むため）と Ed25519（署名のため）の鍵の組を持つ。旅行の鍵は、使い捨ての X25519 の鍵と席の公開鍵の ECDH → HKDF-SHA-256 → AES-GCM で包み、包んだものを席に置く。席の秘密鍵は、席のパスキーの PRF から導いた鍵で包んで席に置き、開いた端末では取り出せない `CryptoKey` として IndexedDB に持つ。パスキーの無い席は、その端末の IndexedDB にだけ持つ
- **新しいメンバーへの受け渡し（確認コード）**: 席を取ったメンバーは、鍵を持つメンバーから旅行の鍵を受け取るまで旅程を読めない。新しいメンバーのブラウザは、先に自分の公開鍵と乱数のハッシュ（コミットメント）だけを Host に預け、鍵を持つメンバーが「渡す」を押すと、互いの公開鍵が Host を中継して届く。両方の画面に 6 桁の確認コードが出るので、チャットや口頭で伝え合い、それぞれ相手のコードを入力する。両方が合ったときだけ、渡す側のブラウザが旅行の鍵を包み、受け取る側のブラウザが開く。合わなければ何も置かず、何も受け取らない
- 確認コードは秘密ではなく、旅行の連絡に使っているチャットに貼ってよい。運用者が Host で公開鍵をすり替えても、偽の旅行の鍵を渡そうとしても、コードが合わない（先にハッシュを預けるので、一致するコードを後から探せない。1 回の試みで通るのは 100 万分の 1）
- 確かめ合った 2 つの席は、互いの公開鍵に署名して残す。鍵を替えるとき、owner のブラウザはこの署名をたどれる席にだけ新しい鍵を包む（§5.5）
- 鍵を渡せるのは、旅行の鍵を持つメンバーならだれでも（役割を問わない）。鍵を渡しても席は増えない
- **鍵の預かり・運用者による回復は無い**。パスキーで戻れば同じ鍵で読める。パスキーが無い・失ったときは、鍵を持つ他のメンバーと確認コードを合わせ直す。鍵を持つメンバーがいなくなった旅行は、だれにも読めない。`aws/recover.ts` で出し直した owner 席も、ほかのメンバーから確認コードで鍵を受け取るまで読めない（§2.4.1）

### 5.2 暗号化するもの・平文に残すもの

暗号化した旅行（§5.4 で移した後、または owner が初めに暗号化した後）の項目ごとの扱い。暗号化は記録ごと（予定 1 件、投稿 1 件、準備リスト 1 行など）で、Host は記録の id・種類・だれが書いたか（席）を平文で見て、役割ごとに足し・替え・消しを検査する。

| データ | 旅行の鍵の暗号文 | 平文（運用者に読める） |
|---|---|---|
| 旅行の設定（Spec） | 題・概要・行き先・ページの名前・日ごとの見出し・表紙の言葉・同行者の名前 | 形の版・言語・タイムゾーン・旅行の日程・ページの構成と種類・見た目（テーマの型と色）・参加者にできること・追記期間と削除期限・書き出しの形 |
| 予定 | 種類・状態・題・場所・説明・タグ（1 件で 1 つの暗号文） | id・日付・開始と終了の時刻・仮置きの印・タイムゾーン・版 |
| 候補・相談・思い出 | 書いた人の名前・本文 | id・投稿時刻・予定にしたか・思い出に入れたか・書いた席 |
| 準備リスト | 項目名 | id・チェックの有無 |
| 費用メモ | 項目名・金額・説明（Host は合計しない） | id |
| メモ | 本文 | — |
| 足あと | 位置（緯度・経度・精度）・残したときの名前 | id・残した席・時刻・自動で残した点か |
| メンバー・招待 | メンバーの名前・招待の名前 | 役割・席数・期限・端末の目印（User-Agent から作る）・登録日・最終利用・パスキーの公開鍵、Host が付けた名前（招待の「自分用」「招待リンク」）。席の既定の名前（「オーナー」「メンバーN」）は owner のブラウザが開いたときに暗号化し直す |
| 招待とオーナーの履歴 | —（名前を持たず、招待と席の id を持つ。画面が名前に戻す） | 操作・時刻・役割・端末、「発行者」「作成者」の行 |
| 写真 | 画像（表示用・サムネイル）・位置・一言・写真ごとの鍵 | id・上げた席・上げた時刻・撮影日時・寸法・手で選んだ予定の id・暗号文の長さ |
| 自分だけの予定・日記 | 題・本文・場所（旅行の鍵ではなく席ごとのメモの鍵。§5.6） | id・種類・日付・時刻・書いた時刻 |

- 暗号文は `<カプセルの id>/<記録の種類>/<記録の id>/<欄>` を追加認証データにする。運用者が暗号文を別の旅行・別の記録・別の欄に入れ替えると開けない（画面は「この端末で開けない記録が N 件あります」と出す）
- ただし、予定の日付・時刻は Host が並べ替えのときに書き換えるので追加認証データに入れない。運用者は予定の日付・時刻を気づかれずに書き換えられる（中身は読めない）。同じ記録を古い暗号文に戻すこと（巻き戻し）、記録を消すことも見つけられない
- **運用者に残るもの**（暗号化の後も読める）: 旅行の日程・タイムゾーン・削除期限・ページの構成・色、予定の件数と日付・時刻、投稿・準備リスト・費用メモの件数とだれ（どの席）がいつ書いたか、足あとと写真の件数・時刻・だれのものか、写真の撮影日時と寸法と手で載せた予定、暗号文の長さ（詰め物はしない）、メンバーの数と役割・端末の目印、ログ（§5.7）
- 暗号化する前の旅行（平文の旅行。§5.4）は、上の旅行の鍵の暗号文の欄も含めて運用者に読める。自分だけの予定・日記の題・本文・場所だけは、平文の旅行でも席ごとのメモの鍵の暗号文（§5.6）

### 5.3 暗号化した旅行で Host にできないこと

Host が暗号文について見るのは、記録の形（暗号文の形と長さの上限）・件数・だれ（どの席・役割）がどの記録を足し・替え・消すか・平文の日付と時刻・全体の大きさだけ。中身を使う処理は画面（ブラウザ）が行う。

- **書き出し**（ZIP・Markdown・旅程のページ）: 画面が開いた旅程から作る。Host の `export`・`export.md`・`export.html` は 409（§3.2）
- **チャットで直す・1 つ前に戻す**: 画面が渡す文を作り、貼った返事を検査して差分を出し、次の旅程の暗号文を送る。Host は役割・共有終了・版の一致・平文の部分・期限と、変えてはいけない暗号文（editor の反映の Spec、思い出、残る投稿の席と時刻）が変わっていないことを見る。Host の `GET revise`・`revise/check` は 409。この端末で開けない記録があるときは、反映でその記録が消えるので、画面は「チャットで直す」「1 つ前に戻す」を出さない
- **ここで直す**（自分の API キー）: ブラウザが Anthropic へ直接送る（§5.8）。Host の `revise/assist` は 409
- **中身の検査**: 字数・URL が https か・足あとの範囲・写真の画像の形は、画面が暗号化の前と開いた後に検査する（他のメンバーが書いた危ない URL をリンクにしない）。Host は平文の部分（id の重なり、日付が旅行期間の中か、件数、大きさ、暗号文の形）だけを検査する
- **候補を予定にする**: 予定の暗号文は画面が作り、Host は置き場所と時刻だけを決める
- **題の確認**（完全削除・大きな変更・1 つ前に戻す）: 画面が開いた題と比べる
- 運用者の一覧（`aws/capsules.ts`）は、どの旅行についても題・旅程・メンバーの名前を出さず、暗号化したかどうかを出す
- **閉じない経路**: 画面の JavaScript は運用者が配る（S3 の `dist/public/`）ので、復号した旅程や旅行の鍵を送り返すコードを配れば読める。メンバーが旅程を書き出して渡す・画面を撮って渡すことも防がない

### 5.4 平文の旅行を移す

作成者と CLI の発行者は平文の旅程を送り、Host が検査して平文で置く。owner の席を取ったブラウザが旅行の鍵を作り、旅程・1 つ前の旅程・足あとの位置と名前・全部の席と招待の名前を暗号化して、1 回の要求（`POST /v1/c/:id/seal`）で置き直す。

- 置き直しは owner の重要操作で、パスキーでの本人確認が要る（§2.2）。WebAuthn の無いブラウザでは移せないので、別のブラウザで開くよう案内する
- 置き直すと、保存は版の一致を条件に 1 回で書き換え、使わなくなった部分を消すので、平文の古い版は表に残らない（表にポイントインタイムリカバリは無い。§5.9）
- 読んだ後に足あと・席・招待が増えた・消えたときは 409 で、画面が読み直して移し直す。暗号化の前の履歴の行は招待・席の id を持たないので、名前を暗号化せずに消す。自分だけの予定・日記はもとから席ごとの鍵で暗号化してあるので触らない
- 暗号文は平文のおよそ 4/3 になる。カプセルの上限に入らないときは、先に 1 つ前の旅程を捨てて置き直す
- 移した後、他のメンバーは鍵を受け取るまで読めない（§5.1）。移す前、owner 以外のメンバーの画面には「オーナーが開くと、この旅行は運用者にも読めない形になります」と出る
- **平文で置かれる間**: (1) 発行から owner が席を取って移すまで（受付は 3 日。席が取られなければ削除期限か、`aws/recover.ts` で出し直した招待が引き換えられるまで）。(2) 暗号化を始める前に発行され、owner がまだ新しい画面で開いていない旅行（移されなければ削除期限まで）
- **暗号化を始めた後に発行した旅行**: Host の設定 `CAPSULE_SEALED_FROM`（AWS はスタックのパラメータ `SealedFrom`。`aws/README.md` の「旅程の暗号化を始めた後に発行した旅行（SealedFrom）」）の時刻より後に発行された平文の旅行は、owner が移すまで、移すための操作とログアウト・削除のほかを 409「オーナーがこの旅行を移すまで開けません」で断る。空なら扱いを始めていない
- 発行できる旅程の大きさは、移した後もカプセルの上限に入るように 1,200,000 バイトまで（超えれば 413）
- 古い画面から暗号化した旅行への要求は 409「画面を更新してください」（古い画面は暗号文を描けない）

### 5.5 旅行の鍵を替える

- 今の世代の鍵を持つ席が抜けると（メンバーの失効、owner 以外の招待の交換・引き換え済みの招待の失効、期限の切れた招待）、Host が記録し、owner のブラウザが次に開いたときに鍵を替える。owner の招待の交換と `aws/recover.ts` の後は、新しい owner に替えるかを聞く（端末を替えただけなら要らない）。共有の終了では替えない
- 替えるとき、owner のブラウザが新しい世代の旅行の鍵を作り、署名をたどれる席（§5.1）ごとに包んで、owner の席の Ed25519 で署名する。メンバーのブラウザは、署名した席が owner で、自分の席からその席まで署名をたどれ、署名が通るときだけ受け取る。運用者が `aws/recover.ts` で作った owner 席は、だれかと確認コードを合わせるまでたどれないので、その席の置いた鍵は受け取られない
- 替えた後、Host は古い世代の暗号文の書き込みを断る。1 つ前の旅程（元に戻す 1 世代）は消える。写真は、写真ごとの鍵・位置・一言だけを新しい世代で封じ直し、画像は送り直さない
- 暗号化した旅行で、owner のほかに今の世代の鍵を持つ席が無ければ、owner の招待の交換は 409 で断る（交換すると旅程をだれも読めなくなる）。先に別の端末かメンバーに鍵を渡す
- **限界**: 抜けた人は古い鍵を持っているので、抜けた人と運用者が組めば、鍵を替えても以後の変更を読まれうる（メンバーのブラウザは、だれが抜けたかを Host からしか知れない）

### 5.6 自分だけの予定・日記の鍵

自分だけの予定・日記（§1.3）の題・本文・場所は、旅行の鍵ではなく**席ごとのメモの鍵**（AES-GCM 256）で暗号化する。メモの鍵はその席のパスキーの PRF から導いた鍵で包んで席に置き、owner・同行者・運用者・`aws/recover.ts` で席を出し直した人のだれにも読めない。項目ごとの平文と暗号文、端末から消すとき、暗号文の入れ替え、失ったとき（新しい鍵は作らず、owner に失効と再招待を頼む。古い席のメモは消える）、チャットに渡したもの、防げないものは §1.4 の「運用者にも読めないもの」に書いた。

### 5.7 ログに残るもの

AWS に配置したときのログ（どれも CloudWatch Logs）:

| 何が | どこに | 何日 |
|---|---|---|
| 全要求の時刻・接続元 IP・メソッド・パス（カプセルの id を含む）・status・応答の大きさ・User-Agent・配信の結果の種類・処理時間 | `/capsule-host/<スタック名>/cdn`（CloudFront の配信ログ。us-east-1。`aws/edge-logs.yaml`） | 90 日 |
| Host が断った要求（4xx / 5xx）のカプセルの id・action・メソッド・status・理由コード・接続元 IP | `/capsule-host/<スタック名>/web`（と `web.local`。`"kind":"refused"` の行） | 90 日 |
| 関数の開始・終了・実行時間の行、期限の掃除や生成の失敗の行（理由コードだけ） | `/aws/lambda/<関数名>` と上の `web` | 90 日 |

- **接続元 IP と User-Agent は個人の情報になり得る**。90 日で消え、旅行の削除（完全削除・運用者の強制終了・期限）では消えない
- **残さないもの**: Cookie、招待の秘密（URL の `#` の後はブラウザから送られない）、クエリ文字列、要求と応答の本文、旅程の題や中身、API キー、生成の希望文と返事、例外の文
- ログの目的は、不審なアクセスがあったか・どの旅行に届いたかを後から確かめること。読めるのは運用者だけ

### 5.8 地図データ・写真・API キー

**地図データ**

- 足あとの地図の背景は、OpenStreetMap のデータから Protomaps が作る地図データ（PMTiles）を、運用者が自分たちの配信元（Assets バケットの `map/`）に置いて配る（作り方は `aws/README.md` の「足あとの地図の背景（地図データ）」）
- 地図に「© OpenStreetMap contributors」を出し、OpenStreetMap の著作権とライセンスのページ（`https://www.openstreetmap.org/copyright`）へリンクする。地図データは ODbL（Open Database License）の派生物
- 閲覧者のブラウザは、地図の部品と地図データを自分たちの配信元からだけ取り、外部のタイル配信サービス・フォント・API キーを使わない（CSP の `img-src` は `'self'`・`data:`・`blob:`）。地図を見る・動かすだけでは、閲覧者の IP・地図で見ている範囲・足あとの座標のどれも外部に渡らない
- **外部に渡るもの**: メンバーが「地図 ↗」を押したときだけ、予定・日記なら場所の名前、足あと・写真なら座標を検索語にして Google マップを新しいタブで開く。その名前か座標と、押した人の IP が Google に渡る。予定の座標は旅程を作る・直すチャットの LLM が付け、Host は地名から位置を引かない（外部のジオコーディング API を使わない）

**写真**

- **既定で無効**。運用者が `CAPSULE_PHOTOS=1`（AWS はスタックのパラメータ `Photos`）にしたときだけ上げられる
- 画像は、ブラウザが写真ごとの鍵で暗号化した bytes（表示用とサムネイル）のまま、構造化データとは別の非公開の置き場に置く（ローカルは `<データ置き場>/media/`、AWS はスタックの S3 `Media`。公開アクセスを全部ブロックし、配信の経路も署名付き URL も持たず、Web Function が席の Cookie を見て返す）。写真ごとの鍵・位置・一言は旅行の鍵の暗号文（§5.2）。平文の旅行には上げられない
- 上げるブラウザが画像を描き直して EXIF・GPS・XMP・コメントを落とし、見るブラウザも復号した後にもう一度確かめてから表示する。撮影日時は平文、位置は暗号化した写真の情報にだけ残る
- 写真は旅行のメンバー全員（閲覧者を含む）が見る。写真に写った本人確認書類・QR コード・他人の顔や住所は、暗号化しても同行者全員には見えるので上げない（§1.4）
- 端末に残るもの: 見た画像の暗号文（`Cache-Control: private, max-age=3600`）と、開いている間の `blob:` の画像は、その端末のもの

**API キー**（Anthropic）

- **作成者の鍵**（新しい旅行の生成。§1.5）: 登録のときに Host が Anthropic に有効かを確かめ（`models.list`）、Host の秘密（`CAPSULE_HMAC_KEY`）から HKDF で導いた鍵の AES-256-GCM で封じ（作成者の id を追加認証データにする）、AWS は SSM Parameter Store の SecureString、ローカルは SQLite の `creator_keys` に置く。値はどの応答にもログにも出さず、登録の有無だけを返す。生成のたびに Host が開き、希望文と一緒に Anthropic に送る。最後に使ってから 30 日で定期の掃除が消し、作成者を失効すると消え、作成者は自分で消せる（登録・置き換え・削除はサインインから 5 分以内）。**運用者は Host の秘密と置き場の両方を読めるので、この鍵は運用者からは守られない**（運用する人を信頼して登録する）。生成の費用は鍵の持ち主に掛かる
- **席の鍵**（旅行の中の「ここで直す」。owner・editor が自分の鍵を登録する）: 平文の旅行では、作成者の鍵と同じ方式で封じて（`<カプセルの id>:<席の id>` を追加認証データにする）席に置き、Host が開いて今の旅程と頼みを Anthropic に送る。暗号化した旅行では、ブラウザが鍵を確かめてから、席のパスキーの PRF から導いた鍵で包み、包んだものだけを席に置く。Host は開けない。直すときはブラウザが包みを開き、開いた旅程と頼みを Anthropic に直接送る（CSP の `connect-src` は `'self'` と `https://api.anthropic.com` だけ）。旅行を暗号化すると、平文の間に席に置いた鍵は消える。鍵は席のもので、他のメンバーや作成者は使えない。席や旅行が消えると一緒に消え、本人が消せる
- Anthropic に送った旅程・希望文・頼みは、Anthropic の扱いになる。Host は希望文・鍵・返事をログに書かない

### 5.9 削除とバックアップ

- **期限**: 削除期限（`purgeAt`）は作成から最大 180 日で、既定は旅行の終了日 + 30 日（§3.1）。期限を過ぎた旅行は、掃除を待たずに要求のたびに 410 で断る。定期の掃除（AWS は 5 分ごと、ローカルは 1 分ごと）が行を空にする
- **完全削除**（owner。旅行の題の入力とパスキーでの本人確認）と**運用者の強制終了**（`aws/capsules.ts`）は、その場で行を空にする。取り消せない
- **写真**: 旅行の削除（完全削除・強制終了・期限）は、行を空にする前にその旅行の画像をすべて消す。消せなければ行を残して次の掃除でやり直す。AWS の `Media` には、作成から 181 日で消える規則を最後の歯止めとして付ける。上げた本人・owner・editor が写真を消すと、すぐ置き場から消える
- **削除の後に残るもの**: 空にした行（中身・題・メンバーを持たない、削除の時刻と期限だけの墓標）を 30 日残してから消す。ログ（§5.7）は 90 日。メンバーの端末に残ったもの（書き出したファイル、画像のキャッシュ、開かれない端末の鍵。§1.4 の「端末から消すとき」）は、その端末のもの
- **共有終了・失効**: 消えた席の自分だけの予定・日記は一緒に消える（§3.3）。足あと・写真は旅行の記録として残る
- **バックアップを取らない**: テーブルのポイントインタイムリカバリもオンデマンドバックアップも使わない（テンプレートに有効にする項目も無い）。Host の約束は「期限で消える」ことで、バックアップは消したはずの旅程の写しを残すため。旅行の後に残したいものは owner が「旅を保存」で手元に持ち出す（Host は保管庫ではない）。スタックを誤って消したときの一括消失は、テーブルとバケットの `DeletionPolicy: Retain` で防ぐ
- **失うもの**: テーブルの破損や誤操作が起きると、進行中の旅行は戻らない。旅行中も「旅を保存」で書き出しておく
- 運用者が自分でバックアップを取って復元すると、復元した時点より後の削除・期限の短縮・招待とメンバーの失効・owner リンクの交換・共有の終了・パスキーと作成者の失効がすべて取り消される（`aws/README.md` の「バックアップ方針」）
- 「削除」は、Host の保存先からの削除と、すぐに読めなくなることを指す。AWS の内部で消去が済む時期は AWS の方針による
